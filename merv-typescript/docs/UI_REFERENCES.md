# UI references (founder brief, 2026-09-16)

Visual reference: **problemma.ai** — a React Flow canvas of research tasks. What it looks like: a white top bar with a back link, the research question as the page title, and plain counts ("Tasks: 17 · Pending: 0 · Completed: 17") with a user avatar; a very light gray ground; nodes as white rounded cards with a soft 1px shadow and a 3px coloured left edge per task type; each card opens with an uppercase kind label in the type colour with an emoji icon (🔍 FIND SIMILAR PROBLEMS, 📚 GET PAPERS, 📊 ANALYZE RELEVANCE, 💡 PROPOSAL, ✏️ EVALUATE SOLUTION), then a two-line title, then a footer "● COMPLETED" in small gray caps; gray curved edges with tiny labels ("retrieves", "analyzes", "generates"); a "Canvas Legend" panel listing task types with coloured dots (purple, blue, teal, gray, red); a minimap. Clean sans (Inter-like), generous whitespace, nothing decorative.

Merv is a review-gated research system: agents propose plans, run experiments, submit evidence, undergo adversarial review; plans and results must pass gates; waves of experiments lead into reviewed reflections; the record preserves how a result was reached. The web UI is where a scientist supervises work and interrogates evidence. Central question: **what did the agents do, why should I believe the result, and does anything need my intervention?**

## References to translate (study the named surfaces; borrow mechanics, not skins)

1. **GitHub** — pull request reviews (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews) and Actions workflow visualization (https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph). Borrow: review state legible at the top of an experiment (which revision was reviewed, latest verdict, unresolved findings, what happens next); feedback attached to the thing judged; the sequence submission → criticism → correction → re-review. Do not copy the code-first layout or human approval of every transition.
2. **Weights & Biases** — reports (https://docs.wandb.ai/models/reports/edit-a-report) and artifact lineage (https://docs.wandb.ai/models/artifacts/explore-and-traverse-an-artifact-graph). Borrow: report-first experiment page (question, conclusion, key comparisons, then chart, run, artifact); freezing a report's run set → make it unmistakable whether one is viewing reviewed evidence or a newer changing state; experiment vs its runs. Do not copy a home screen of metric panels.
3. **Linear** — Inbox (https://linear.app/docs/inbox), agents in Linear (https://linear.app/docs/agents-in-linear), the redesign article (https://linear.app/now/how-we-redesigned-the-linear-ui). Borrow: an attention layer above the record (Needs you / Blocked / Active / Recently reviewed), split-pane scan-and-inspect, a question addressed to the scientist looks different from an agent's routine note; the hierarchy of sidebar, header, filters, contextual panels. Do not copy just the colours, type or compactness.
4. **Benchling** — notebook (https://www.benchling.com/notebook). Borrow: the experiment as one coherent scientific record (question, approved plan, deviations, results, findings, materials as parts of one document); distinguish working draft → submitted revision → reviewed record; amendments add to history. Do not copy wet-lab inventory or compliance forms.
5. **Dagster** — UI guide (https://docs.dagster.io/guides/operate/webserver) and asset catalog (https://docs.dagster.io/guides/observe/asset-catalog). Borrow: graph interactions (focus a node and neighbours, filter, collapse groups, contextual detail panel); overview → problematic step → logs with selection preserved. Do not import pipeline semantics: an edge meaning "contradicts this claim" must not look like "ran after this job".
6. **Braintrust** — evaluate (https://www.braintrust.dev/docs/evaluate) and annotate (https://www.braintrust.dev/docs/annotate). Borrow: a finding beside its evidence; a "revise" verdict expands into understandable objections; finding cards (concern, evidence referenced, blocking or not, how the next submission addressed it); previous vs current attempt comparison. Do not copy a single score as validity or turning the scientist into an annotator.
7. **incident.io** — post-incident flow (https://docs.incident.io/post-incident/post-incident-flow) and timeline (https://docs.incident.io/post-incident/timeline). Borrow for reflections: what happened, what we learned, what changed in our understanding, what we will do differently; coverage and unresolved obligations. Do not import urgency.
8. **Elicit** (https://elicit.com/). Borrow: clicking a claim reveals supporting and challenging evidence with the excerpt or figure at hand; an evidence matrix (source, scope, limitations, relation to the claim); keep literature evidence and Merv-generated evidence distinguishable.
9. **Runpod** — manage pods (https://docs.runpod.io/pods/manage-pods). Borrow: each sandbox in research terms (which experiment, what it is doing, uptime, expiry, what happens to outputs on release); consequences of destructive actions inside the confirmation. Secondary reference.

## Surface map the founder proposed

| Merv surface              | Reference combination    | Main design question                                                 |
| ------------------------- | ------------------------ | -------------------------------------------------------------------- |
| Project home              | Linear + Dagster         | What changed, what is blocked, and where should I look?              |
| Experiment detail         | GitHub + W&B + Benchling | What was attempted, what passed review, and where is the evidence?   |
| Reviewer findings         | GitHub + Braintrust      | What is wrong, what does it refer to, and was it addressed?          |
| Claims and research graph | Elicit + Dagster         | What supports this claim, what challenges it, and how did it evolve? |
| Reflection                | incident.io + Benchling  | What did the wave teach us, and what changes next?                   |
| Sandboxes                 | Runpod + Dagster         | What is running, why, and what are the consequences of intervening?  |

Two distinctions guide every screen: separate execution state, review state and scientific outcome ("execution completed", "review passed", "hypothesis contradicted" can all be true at once); keep commentary separate from authority (the feed explains and directs attention; the verdict, artifact revision and claim status are the authoritative destinations).

Strongest recommendation: build the experiment detail around GitHub's review model and W&B's evidence model, inside a Linear-like supervision interface; Benchling supplies the scientific-record discipline.
