# UI references (founder brief, 2026-09-16)

Visual reference: **problemma.ai** — a React Flow canvas of research tasks. What it looks like: a white top bar with a back link, the research question as the page title, and plain counts ("Tasks: 17 · Pending: 0 · Completed: 17") with a user avatar; a very light gray ground; nodes as white rounded cards with a soft 1px shadow and a 3px coloured left edge per task type; each card opens with an uppercase kind label in the type colour with an emoji icon (🔍 FIND SIMILAR PROBLEMS, 📚 GET PAPERS, 📊 ANALYZE RELEVANCE, 💡 PROPOSAL, ✏️ EVALUATE SOLUTION), then a two-line title, then a footer "● COMPLETED" in small gray caps; gray curved edges with tiny labels ("retrieves", "analyzes", "generates"); a "Canvas Legend" panel listing task types with coloured dots (purple, blue, teal, gray, red); a minimap. Clean sans (Inter-like), generous whitespace, nothing decorative.

Merv is a review-gated research system: agents propose plans, run experiments, submit evidence, undergo adversarial review; plans and results must pass gates; waves of experiments lead into reviewed reflections; the record preserves how a result was reached. The web UI is where a scientist supervises work and interrogates evidence. Central question: **what did the agents do, why should I believe the result, and does anything need my intervention?**

## References to translate (study the named surfaces; borrow mechanics, not skins)

1. **GitHub** — pull request reviews (https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews) and Actions workflow visualization (https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph). Borrow: review state legible at the top of an experiment (which revision was reviewed, latest verdict, unresolved findings, what happens next); feedback attached to the thing judged; the sequence submission → criticism → correction → re-review. Do not copy the code-first layout or human approval of every transition.
2. **Weights & Biases** — reports (https://docs.wandb.ai/models/reports/edit-a-report) and artifact lineage (https://docs.wandb.ai/models/artifacts/explore-and-traverse-an-artifact-graph). Borrow: report-first experiment page (question, conclusion, key comparisons, then chart, run, artifact); freezing a report's run set → make it unmistakable whether one is viewing reviewed evidence or a newer changing state; experiment vs its runs. Do not copy a home screen of metric panels.
3. **Linear** — Inbox (https://linear.app/docs/inbox), agents in Linear (https://linear.app/docs/agents-in-linear), the redesign article (https://linear.app/now/how-we-redesigned-the-linear-ui). Borrow: an attention layer above the record (Needs you / Blocked / Active / Recently reviewed), split-pane scan-and-inspect, a question addressed to the scientist looks different from an agent's routine note; the hierarchy of sidebar, header, filters, contextual panels. Do not copy just the colours, type or compactness.
4. **Benchling** — notebook (https://www.benchling.com/notebook). Borrow: the experiment as one coherent scientific record (question, approved plan, deviations, results, findings, materials as parts of one document); distinguish working draft → submitted revision → reviewed record; amendments add to history. Do not copy wet-lab inventory or compliance forms.
5. **Dagster** — UI guide (https://docs.dagster.io/guides/operate/webserver) and asset catalog (https://docs.dagster.io/guides/observe/asset-catalog). Borrow: graph interactions (focus a node and neighbours, filter, collapse groups, contextual detail panel); overview → problematic step → logs with selection preserved. Do not import pipeline semantics: an edge meaning "contradicts this claim" must not look like "ran after this job".
6. **Braintrust** — evaluate (https://www.braintrust.dev/docs/evaluate) and annotate (https://www.braintrust.dev/docs/annotate). Borrow: a finding beside its evidence; a "revise" verdict expands into understandable objections; finding cards (concern, evidence referenced, blocking or not, how the next submission addressed it); previous vs current attempt comparison. Do not copy a single score as validity or turning the scientist into an annotator.
7. **incident.io** — post-incident flow (https://docs.incident.io/post-incident/post-incident-flow) and timeline (https://docs.incident.io/post-incident/timeline). Borrow for reflections: what happened, what we learned, what changed in our understanding, what we will do differently; coverage and unresolved obligations. Do not import urgency.
8. **Elicit** (https://elicit.com/). Borrow: clicking a claim reveals supporting and challenging evidence with the excerpt or figure at hand; an evidence matrix (source, scope, limitations, relation to the claim); keep literature evidence and Merv-generated evidence distinguishable.
9. **Runpod** — manage pods (https://docs.runpod.io/pods/manage-pods). Borrow: each sandbox in research terms (which experiment, what it is doing, uptime, expiry, what happens to outputs on release); consequences of destructive actions inside the confirmation. Secondary reference.

## Surface map the founder proposed

| Merv surface              | Reference combination    | Main design question                                                 |
| ------------------------- | ------------------------ | -------------------------------------------------------------------- |
| Project home              | Linear + Dagster         | What changed, what is blocked, and where should I look?              |
| Experiment detail         | GitHub + W&B + Benchling | What was attempted, what passed review, and where is the evidence?   |
| Reviewer findings         | GitHub + Braintrust      | What is wrong, what does it refer to, and was it addressed?          |
| Claims and research graph | Elicit + Dagster         | What supports this claim, what challenges it, and how did it evolve? |
| Reflection                | incident.io + Benchling  | What did the wave teach us, and what changes next?                   |
| Sandboxes                 | Runpod + Dagster         | What is running, why, and what are the consequences of intervening?  |

Two distinctions guide every screen: separate execution state, review state and scientific outcome ("execution completed", "review passed", "hypothesis contradicted" can all be true at once); keep commentary separate from authority (the feed explains and directs attention; the verdict, artifact revision and claim status are the authoritative destinations).

Strongest recommendation: build the experiment detail around GitHub's review model and W&B's evidence model, inside a Linear-like supervision interface; Benchling supplies the scientific-record discipline.

## Tinker (Thinking Machines) — added 2026-09-16

**What it is.** A hosted fine-tuning API with a console. Its own claim: "A cloud training API that gives you full control over your data, algorithms, and models. Write training loops locally — Tinker handles the GPUs", with the division of labour stated once: "Tinker handles scheduling, tuning, resource management, and infrastructure reliability so you can focus on the training data and algorithms" (product page, thinkingmachines.ai/tinker). The whole API is four primitives — `forward_backward` ("Perform a forward pass and a backward pass, accumulating the gradient"), `optim_step` ("Update weights based on the accumulated gradient"), `sample` ("Generate tokens for interaction, evaluation, or RL actions"), `save_state` ("Save training progress for resumption") — and the praise the product page prints for itself is about restraint: "a small set of primitives that compose cleanly to express a rich space of algorithmic ideas" (Leopold Haller, Axiom Math, on the product page). It belongs in this brief because Merv is the same shape of system seen from the other side: a small tool surface an agent composes against, plus a console a person supervises from. Its data model is also ours — "Project: the data-isolation boundary", "every session belongs to a project", and a checkpoint "inherits its project from the session that produced it" (Data Model & Permissions) — which is exactly `Caller.projectId` in `packages/contracts/src/index.ts`.

**The console's surfaces and their columns** (observed signed in, 2026-09-16; the docs picture none of them). Sidebar: Home, Projects, Sessions, Checkpoints, Playground (New), Docs; Manage: API Keys; Admin: Users, Teams, Usage, Billing.

| Surface     | Contents and columns                                                                                                                                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Projects    | Project name, Project ID, Shared with, # Sessions, Estimated checkpoints, Estimated storage, and a Manage action. The default project reads "shared with: Entire organization".                                                    |
| Sessions    | A "My sessions" scope switch and a search by session ID prefix, then Session ID, Status, Created, Checkpoints, Checkpoint storage, Project, Metadata.                                                                              |
| Checkpoints | The sentence "This shows checkpoints created by you in projects you can access", then two totals (TOTAL OWNED CHECKPOINTS, TOTAL OWNED CHECKPOINT STORAGE), then Checkpoint ID, Type, Created, Size, Expires, Full path, Metadata. |
| Usage       | Three summary cards and one chart.                                                                                                                                                                                                 |
| Home        | An open-weight-models hero, a grid of doc links (Get Started, Models & Pricing, LoRA Primer, Session Metrics, CLI Reference, Storage, Recipes and the rest), then Sessions and API keys inline as lists.                           |
| Playground  | A chat box with prompt chips.                                                                                                                                                                                                      |

The CLI prints the same table — `tinker checkpoint list` returns Checkpoint ID, Type, Size, Published, Created, Expiration, and "All commands support `-f, --format [table|json]` for output format" — and a stored object's identity is a path rather than a name: "All checkpoint commands take a `CHECKPOINT_PATH` in the format `tinker://run-id/sampler_weights/final`" (CLI Reference › tinker checkpoint). Permissions are three project roles, and the durable-object verbs are owner-gated: "Only the owner of the training run can delete checkpoints", "Deleting a checkpoint is permanent", and a read-only project allows "no new sessions, training runs, or checkpoint saves" (Data Model & Permissions).

Visually: white ground, grey table skeletons while loading, an em dash where a total is not yet known, one scope switch and one search per tabular page, and a serif display face on the marketing hero only — which Merv ignores, having withdrawn the serif on the same day. The founder's own reading of the console, which is a ruling for Merv and not an observation: "did you catch how minimalistic Tinker UI is? There is no chrome whatsoever, only lines there exist to separate things, things don't have borders, etc.. The color is too sterile, but we can handle that." Both halves bind — take the restraint, refuse the sterility, and the thing that keeps Merv warm where Tinker is cold is the kind colour and its icon, which Tinker has no equivalent of.

**Worth stealing.**

1. **The durable-object page: one row per retained thing, with size and lifetime as columns.** Tinker gives each of its two durable objects — sessions and checkpoints — a top-level page whose every column is a fact about durability (Size, Expires, Full path, Checkpoint storage), and dresses neither as a dashboard. Merv holds the same two objects under other names: agent leases, which carry a real `expiresAt`, and retained artifacts and exhibits, which are immutable, hashed and carry a real `size`. The borrow is the ownership sentence and the pair of totals above the rows, not the storage frame around them.
2. **Estimated, and the em dash.** The Projects table puts the hedge in the column label itself — "Estimated checkpoints", "Estimated storage" — the Session Metrics page says of its throughput numbers "Because of this, these numbers are an estimate", and the console prints an em dash where a total has not arrived rather than a zero. That is `docs/UI_LEGACY_PATTERNS.md` checklist rule 4 already being practised by somebody else, and it is the cheapest honesty a supervision UI can buy.
3. **The primitive set as the vocabulary.** Four verbs, one documented sentence each, and everything else in the product is composition; the console invents no fifth verb for the person, so what a page can do is exactly what the API can do. Merv's "never" list is largely a list of verbs the browser must not invent — Resolve, Assign, Retract, Snooze, Approve-then-Witness — and this is that same rule stated positively and made checkable.
4. **No borders: a line only where two things meet.** The console's containers have no boxes at all — a 1px hairline separates a header from its rows and one row from the next, and that is the entire inventory of chrome. It is the founder's ruling above, and it refines rather than replaces the problemma-derived visual language in `docs/UI_DESIGN.md`: the white-card-on-light-ground rule survives only where the box is the object itself, everything else loses its border, radius and shadow, and the kind colour and icon stay exactly as they are, since they are what stops the result reading as sterile.

**What to leave.**

- **The Playground read as a chat box.** Tinker can offer a scratch surface because its product is a model you can talk to. Merv's product is a reviewed record and there is nothing to try out; the one legitimate Merv scratch surface is the reference resolver that already exists on `/knowledge`.
- **Admin, Usage and Billing as planes of the product.** Three summary cards and a spend chart is the "home screen of metric panels" the brief already rules out, wearing a different hat.
- **Publish, unpublish, push-to-Hugging-Face and set-ttl on a retained object.** Those are right for weights a user owns and wrong for evidence a verdict is pinned to: a control that could make an artifact public, private or expiring would make a settled review's evidence negotiable after the fact. Merv has no artifact-delete tool and should not acquire one.
- **The Perfetto trace export** (`tinker session export-trace`, "Open the resulting file in https://ui.perfetto.dev to view the timeline"). That is a microsecond timeline for a performance engineer; Merv's retained evidence artifact is the log, and it is hashed and citable, which is the better property.
- **Metadata as a column.** Both tables end in an untyped dictionary the product cannot say anything about. Merv's equivalent facts — role, stage, attempt, revision, verdict — are typed and belong in named columns.
- **The path as the visible identity** (`tinker://run-id/sampler_weights/final`). Merv identifies a retained file by its hash and names it by its title; a path in the row would be a second identity to keep true.
- **The serif hero.**
