# Graph retirement plan (2026-09-16)

Founder ruling: retire all agent-authored logic graphs; every graph is derived programmatically from the record (a process graph). This plan comes from a five-reader inventory and a planner; it is the brief for the removal agents. Nothing already written is rewritten, purged or hidden: legacy graph artifacts stay readable as plain files.

## The process graph (derived, never authored)

DEFINITION. One derived structure, one shape, for every record kind. Experiments, tasks, research cycles and reflections are all workflow instances, so there is no per-kind graph format and no per-kind writer — there is one derivation and four callers. Nothing in it is parsed from bytes an agent wrote; there is no envelope, no version literal, no node cap, no validator, no `refs` field and no passthrough keys, because nothing is parsed at all.

LAYER 1 — SKELETON (nodes, and every legal edge). Source: WorkflowDefinition (packages/contracts/src/index.ts:437-448) obtained from `ctx.workflows.catalog()` (packages/workflows/src/index.ts:392-397, which returns canonical deep copies of the registered definitions), filtered to the instance's pinned {workflow, version}. One node per `states[]` entry, flagged from `initial` and `terminal[]`; one edge per `edges[]` entry {from, action, to}. This is deployed program code: fingerprinted, version-pinned, and already required to have exactly one registered policy guarding every edge (packages/workflows/src/evaluation.ts:40, 125-129). For experiments the vocabulary is ExperimentStatus (planned, design_review, running, experiment_review, complete, abandoned, failed) and ExperimentTransitionName (submit_design, submit_results, retry_running, abandon, mark_failed) at packages/experiments/src/models.ts:4-14 — but the derivation reads them from the registered definition, never from a hard-coded list.

LAYER 2 — TRAVERSAL (which edges were actually taken, by whom, when). Source: wf_history via `workflows.history(caller, instanceId)` → WorkflowHistoryEntry (packages/workflows/src/index.ts:175, 1166-1195): {instanceId, revision, action, actorId, requestId, fromState, toState, data, createdAt}, one row per recorded transition. Each row stamps its matching skeleton edge as traversed with its revision, actor and timestamp; an edge taken more than once (retry_running, a review return) carries the ordered list of its traversals rather than a boolean, so rework is visible instead of collapsed. Node first-visit times come from the first row whose toState is that node. Untraversed edges stay present and unstamped — the difference between "could have happened" and "did" is the whole point.

LAYER 3 — LIVE POSITION (where the record stands, what is available now). Source: `workflows.evaluate()` → WorkflowDecision (packages/contracts/src/workflow-guidance.ts:45-63): `state` marks the current node; `currentGate`, `revision`, `terminal` label it; `actions[]` (WorkflowActionStatus: action, tool, status ready|needs_input|blocked, blockers[]) stamps each outgoing edge of the current node with its live status and the blocker text that explains it; node-level `blockers[]` attach to the node. Because these come from the same checkAction the real transition runs, the drawn edge status and the actual gate cannot disagree.

LAYER 4 — INTER-RECORD EDGES. Source: `workflows.dependencies()` (packages/workflows/src/dependencies.ts:122-170, computed from wf_dependencies joined to wf_instances and wf_success_states) and the `dependencies[]` already on WorkflowDecision: WorkflowDependency {id, workflow, version, name, state, settled, failed}, in both directions. These are edges between whole process graphs — the dependency chain, which is the only place pipeline semantics are correct.

LAYER 5 — PER-KIND DETAIL, attached to nodes, never a second graph and never inside the generic tool. Each domain already returns it, so the derivation duplicates nothing:

- experiment (experiment.get_state → Experiment, packages/experiments/src/models.ts:96-115): attempts[] {index, startedRevision, endedRevision, previousIndex — the re-entry edge, approvedSubmissionId, approvedReviewId} give the attempt lanes as revision intervals; submissions[] {stage, round, producerId, evidence[], figureIds[], manifestHash, reviewId} give one sealed node per round; evidence[] {role, path, artifactId, hash, attemptIndex, sequence, current, resultFormat, systemGenerated} hang artifact leaves off the attempt that produced them; testedClaimIds (models.ts:19,105, validated against claims.get at index.ts:269 and persisted at 307) are the typed claim edges that replace the retired node `refs`; the metrics exhibit is the system-generated leaf.
- task: the installed task program's instance plus its structured evidence rows and its wf_dependencies edges.
- cycle: the research@2/@3 instance, with its reflection wave and consolidation as dependent instances via layer 4.
- reflection: the REFLECTION_WORKFLOW instance plus its child lens instances (parent/child binding is workflow machinery), with the wave's two surviving outputs (report, change specification) as leaves on the synthesis node. Rendered as the four-rung ladder, this is a process graph written as text.
- any kind: Review.status/verdict/returnTo. `returnTo` is the literal reverse edge — it names the state the record was sent back to and matches a skeleton edge, which the verdict then labels.

INVARIANT, stated so it can be tested: every node is a state of a registered definition; every edge is either a definition edge (optionally stamped with recorded traversals) or a recorded dependency between instances; no field originates in artifact bytes.

PRODUCTION: A SERVER TOOL (`workflow.process` in packages/workflows/src/tools.ts, readOnly, input {instanceId}), not browser derivation. Four reasons, all verified:

1. The skeleton is not browser-reachable. `catalog()` is a synchronous service method and no registered tool returns a WorkflowDefinition — workflow.status_and_next returns a WorkflowDecision or a WorkflowOverview, never the definition. Deriving in the browser would mean hard-coding the five experiment states and the reflection rungs in TSX: a hand-written copy of the program, which is an authored graph again, merely authored by a UI developer instead of an agent.
2. The traversal is not browser-reachable either. `history()` is a service method with no tool. The browser's only transition source is feed.activity, whose input schema is `{after?: number}` strict — forward-only from the oldest event with no subject filter — so a per-record history would be best-effort over a head window and silently incomplete.
3. One derivation serves four record kinds. Browser derivation means four renderers each re-deriving, and they will drift.
4. It follows the project's own precedent for a system-generated document: the metrics exhibit (packages/experiments/src/evidence.ts:243-361) — computed in code, canonical bytes, immutable provenance, systemGenerated. With one deliberate difference: the process graph is computed on read and is NOT pinned as an artifact or attached as evidence. The exhibit is pinned because it summarizes bytes that could later be re-read differently; the process graph is a pure function of records that are themselves immutable, so a stored copy could only drift from them. Pinning it would quietly recreate a stored graph document, which is the thing being retired.

NAMING AND EXPOSURE. Do not reuse the freed name `experiment.graph`: session execution policies are frozen with a policyHash and authorized against that frozen list (packages/sessions/src/index.ts:643,1254), so sessions minted before the removal still carry a grant for that name, and rebinding it would silently resolve an old grant to new semantics. Do not grant `workflow.process` in any session execution policy by default either — agents already get their next step from workflow.status_and_next, so this read exists for readers and the UI and no frozen policy has to change. Net tool-catalog effect: −1 when experiment.graph is unregistered, +1 when workflow.process is registered.

## Legacy records

Nothing already written is rewritten, purged or hidden. The ruling retires what agents are asked to author from now on; it does not authorize editing the record of what was authored before.

STORAGE MAKES THIS NON-OPTIONAL. experiment_evidence.role is `role TEXT NOT NULL` with no CHECK, behind `experiment_evidence_immutable` (BEFORE UPDATE) and `experiment_evidence_no_delete` (BEFORE DELETE) triggers (packages/experiments/src/storage.ts:70-78). experiment_submissions rows are equally immutable and embed whole evidence arrays; artifacts are immutable and undeletable (packages/artifacts/src/index.ts:45-46). Every legacy role='graph' row and every graph.json byte survives by design, and any attempt to purge them aborts at the trigger.

THE SEVEN CONCRETE MEASURES:

1. Narrow the WRITABLE role union only. packages/experiments/src/models.ts:12 becomes 'plan'|'result'|'report'|'exhibit', and a read-side `StoredExperimentRole = ExperimentRole | 'graph'` types ExperimentEvidence.role. Without this, get()/list() type-lie about existing rows and the restart-replay assertion `deepEqual(await experiments.get(...), e)` (tests/experiments.test.ts:579) breaks against any brain that ever completed an experiment.
2. Never recompute a historical manifest. experiment_submissions.record.manifestHash (packages/experiments/src/index.ts:862-868) was digested over an evidence array containing a graph entry. Leave it.
3. Reword review criteria in place, never renumber or delete. packages/experiments/src/index.ts:81 and packages/reflections/src/definitions.ts:58 keep their positions (REFLECTION_CRITERIA stays length 4) because review.submit requires one finding per criterionNumber and past immutable findings are pinned to those positions. Historical reviews keep the old wording: they are evidence of what was actually asked.
4. Do not touch packages/reflections/src/legacy.ts. It exists to serve historical waves their original v2 recipes byte-for-byte. Add at most a one-line comment saying the graph requirement there is historical and must not be copied forward.
5. Keep legacy readers conditional, not deleted. packages/consolidation/src/index.ts:197 keeps its `legacy.graph` branch as `...(legacy.graph ? [legacy.graph] : [])` — it reconstructs the source set of already-completed consolidations, and deleting it would silently shrink them on every read. packages/research/src/index.ts:427 takes the same conditional so a legacy wave still in flight keeps its reviewed graph among its consolidation sources. ApprovedReflection.graph therefore becomes `graph?: Artifact` marked legacy-only rather than being deleted from the type; the forward contracts (ReflectionSubmit, Submission, Reflection) lose it outright.
6. Imported Python-brain history stays verbatim. src/legacy-history.ts:78-95 keeps published_graph_version_id in the reflections column list, and tests/legacy-history.test.ts:104-112, 226-234, 292-300 stay untouched. That column is part of the export spec and the canonical receipt digest that deploy/legacy-rehearsal.mjs:597-614 and 832-839 reconcile; dropping it would break import fidelity and erase which graph a legacy wave published.
7. The bytes stay readable as plain files, with a path to them. packages/ui/web/views/artifacts.tsx:94-138 renders any retained artifact as JSON in a <pre class="doc"> with no role-aware branch — that is the plain-file reader and needs no change. Because packages/ui/web/views/experiments.tsx:37-80 filters evidence bands by the ROLES array, dropping 'graph' from it would make historical graph.json rows invisible on the record page even though they remain in the database and pinned in sealed review manifests; the plan therefore adds one catch-all band rendering any role outside the fixed list under a neutral heading with its normal artifact link.

ALSO PRESERVED AS RECORDS, NOT REQUIREMENTS: verification/experiments.json:81,121,131 and VERIFICATION.md:29,46 are dated records of what was actually verified and must not be hand-edited — a new run after the change produces a new record. Merv/output/reproducibility/** frozen study snapshots and Merv/.claude/worktrees/** (other sessions' checkouts) are out of bounds. docs/EXPERIMENTS_PARITY_REFERENCE.md keeps its graph rows marked "retired by the 2026-09-16 ruling" rather than silently deleted, so a future parity reader does not mistake absence for an unimplemented gap and rebuild it.

WHAT A DERIVED PROCESS GRAPH RENDERS FROM (all four sources verified, with the exact fields):

1. Topology — the states and the legal moves. WorkflowDefinition, packages/contracts/src/index.ts:438-448: `name`, `version`, `initial`, `states: string[]`, `terminal: string[]`, `edges: {from, action, to}[]`. This is a real, programmatically generated, immutable, fingerprinted DAG — exactly what the ruling asks for. GAP: no tool exposes it. workflow.status_and_next (packages/workflows/src/tools.ts:14-44) returns a WorkflowDecision or a WorkflowOverview, never the definition, so a faithful renderer needs a small read (a `workflow.definition` returning states/terminal/edges for a workflow name+version) or it will be reduced to hard-coding the five experiment states in the browser, which is the wrong answer. For experiments the action vocabulary is already typed as ExperimentTransitionName (packages/experiments/src/models.ts:13-14): submit_design, submit_results, retry_running, abandon, mark_failed; states are ExperimentStatus (models.ts:4-11): planned, design_review, running, experiment_review, complete, abandoned, failed.

2. Where this record stands, and what edge is live. workflow.status_and_next with instanceId → WorkflowDecision, packages/contracts/src/workflow-guidance.ts:45-63: `state` (the current node), `currentGate`, `revision`, `terminal`, `available`, `label`, `instruction`, `nextAction`, `actions: WorkflowActionStatus[]`, `blockers: WorkflowBlocker[]`, `references: WorkflowReference[]`, `dependencies: WorkflowDependency[]`, `workStart`. WorkflowActionStatus (L24-32): `action`, `tool`, `instruction`, `status: 'ready'|'needs_input'|'blocked'`, `arguments`, `requiredInput`, `blockers` — so each outgoing edge can be drawn ready / needs input / blocked, with the blocker text on the edge. WorkflowBlocker (L19-23): `code`, `message`, `status`. WorkflowDependency (L9-17): `id`, `workflow`, `version`, `name`, `state`, `settled`, `failed` — cross-record edges between work items; this is the 'graph → job → log applied to the dependency chain' the founder brief asked for, and components.tsx GateBox L404-417 already renders the unsettled subset as links. WorkflowReference (L3-7): `kind`, `id`, `label`. WorkflowWorkStart (L33-44): `instanceId`, `workflow`, `version`, `state`, `revision`, `actorId`, `startedAt`, `eventId` — first activation at the current revision, the only per-node timestamp available without the event log. Omit instanceId and the same tool returns WorkflowOverview (L65-72): `ready[]`, `blocked[]`, `terminal[]`, `unavailable[]`, `workflows: WorkflowDecision[]` — a whole-project process graph in one read.

3. The lanes inside one experiment. experiment.get_state → Experiment (packages/experiments/src/models.ts:96-115): `workflow` (WorkflowSnapshot: state, revision, updatedAt), `attempt` and `attempts: ExperimentAttempt[]` (L81-94: `index`, `startedRevision`, `endedRevision`, `previousIndex` — the re-entry edge, `feedback[]`, `feedbackReviewIds[]`, `approvedSubmissionId`, `approvedReviewId`, `startedAt`, `createdAt`), `submissions: ExperimentSubmission[]` (L62-80: `id`, `attemptIndex`, `stage: 'design'|'results'`, `round`, `subjectRevision`, `producerId`, `sessionId`, `evidence[]`, `figureIds[]`, `manifestHash`, `reviewId`, `createdAt`), `evidence: ExperimentEvidence[]` (L44-61: `role`, `path`, `artifactId`, `hash`, `attemptIndex`, `sequence`, `current`, `resultFormat`, `systemGenerated`, `createdBy`, `createdAt`). Every one of those is a node or an edge nobody authored: attempt lanes bounded by revision intervals, a submission node per round carrying its manifest hash, artifact leaves hanging off the attempt that produced them.

4. The verdicts and the back-edges. review.list → Review (shape declared in packages/ui/web/views/reviews.tsx:31-51): `id`, `subjectId`, `subjectRevision`, `producerId`, `reviewerId`, `artifactIds[]`, `criteria[]`, `status: 'requested'|'started'|'submitted'|'superseded'`, `verdict: 'pass'|'needs_changes'|'fail'`, `returnTo`, `findings[{criterionNumber, status, evidenceIds[], notes}]`, `createdAt`. `returnTo` is the literal reverse edge — it names the state the record was sent back to — and RoundsSpine (experiments.tsx:259-339) already prints it in words. 5. The traversal actually taken, with timestamps and actors. feed.activity → StoredEvent[] (packages/contracts/src/index.ts:109-117): `id`, `projectId`, `actorId`, `type`, `subjectId`, `data`, `createdAt`. Two event types are the edges: `workflow.transition`, emitted at packages/workflows/src/index.ts:1784-1799 with data `{workflow, version, revision, action, from, to, ...eventSource}` — a recorded edge traversal with its action name, its endpoints, its revision and its actor, which is precisely an edge nobody wrote by hand; and `workflow.work_started` at index.ts:968-979 with data `{workflow, version, state, revision}`. views/feed.tsx:94-97 already decodes `data.to`, and L76-105 is the existing precedent for rendering state change from the log.
