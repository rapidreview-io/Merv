# Optional Fleet — workflow v1

Reduced proposal. See [sequence](FLEET_PI_PROPOSAL.md) and mandatory [bootstrap prerequisite](FLEET_BOOTSTRAP_PREREQUISITE.md).

**Ownership.** Fleet provisions/retires machines through Sandboxes. Sessions selects assignments; Runner and code.v2 execute and retain results. One package with optional workflow/API/UI entries. Core uses State, Scope, Sandboxes; workflow adapter also uses Sessions. Sessions does not import Fleet implementation. Missing managed-allocation validators fail closed. Base app builds and works without Fleet.

**Small state model.** Two tables initially: Fleet allocations and Sessions-managed runner bindings. Allocation includes owner/request key and digest, source/project/profile, epoch, desired/observed state, provider operation/sandbox/job IDs, next action/retry, deadlines and retention receipt. It doubles as durable reconciliation intent: no separate request/outbox/heartbeat/fairness tables. Binding includes allocation/epoch, source, exact runner/profile, credential digest/expiry and immutable successful execution ID. Fixed limits/profile are configuration. Existing events record meaningful transitions.

Proposed service methods: request within caller transaction, cancel, inspect, drain, halt. Validate owner/source/project/profile; never accept arbitrary executable commands/images. Pi can later commit its command and capacity request together while Fleet sees only an opaque owner. Minimal Fleet row shows status, owner links and authorized drain/halt controls; reuse Sessions/Sandboxes details.

**PostgreSQL/write budget.** Reserve under the existing State transaction before provider calls; count reserved, provisioning, active, draining, releasing and uncertain machines. Never hold the global writer lock over provider IO. Stable operation/job keys survive retries. No heartbeat history or per-poll durable writes: coalesce liveness in memory and persist lifecycle transitions/coarse lease renewals only. On restart reconcile durable allocations with provider/job state before replacements. Measure transaction counts and dispatch/review latency; changing State's lock is outside scope.

**Demand without a copied scheduler.** First extract candidate eligibility/selection from Sessions.leaseOnce into one Sessions-owned helper accepting its transaction/read snapshot and profile capabilities. Real leasing and prospective-demand reads call the same helper. Keep live-runner admission, settings acknowledgements, receipts and final reservation inside leaseOnce. Prospective demand cannot require an already-existing worker. Characterization tests preserve dispatch-off, source visibility, dependencies, holds, budgets, retry/backoff and workspace compatibility. Runner-specific failures remain lease-time checks; demand is advisory.

Fleet never duplicates predicates or scrapes the capped UI queue. If extraction cannot stay small, review it as its own patch rather than shipping copied rules. One enrollment source/profile per project; deduplicate candidate identity/revision and subtract compatible available/provisioning slots once. Give external spare capacity bounded grace, not an indefinite veto. Occasional empty workers from boot-time races are acceptable and retire promptly. Provisioning does not reserve a task.

**Managed principal.** A restricted identity remains necessary: exact-runner presence, one successful automatic lease, then control/Code transfer for that execution only. Deny manual offers, agent management, administration and arbitrary domain tools. Supervisor holds this credential; harness receives existing frozen assignment authority. One-assignment lifetime simplifies capture/retirement; it does not substitute for OS isolation.

Scope resolves provenance/revocation. Sessions owns input schemas and principal admission; current API provider registration exposes controls. Session tool enforcement remains ToolRegistry.registerSessionPolicy, not Scope.toolPolicy. Code controls retain bound-execution and writer checks.

Within the lease transaction validate current source, epoch, profile and cancellation/drain intent, then atomically bind one successful execution. Unique binding prevents double claims. Empty polls consume nothing. Authenticate before receipt replay. Original request may replay its historical receipt; no different request obtains a successor after completion/expiry. Missing Fleet validator denies managed admission without affecting ordinary runners.

**Lifecycle.** Reserve → provision → launch → ready → run → capture → stop → release. Allocation records distinguish desired stop from observed stop. Reconcile lost responses before another create. Managed Runner claims once, stops admission, captures Code, reports receipt and exits. Current stop is not graceful drain; add only this narrow mode. Cancel-versus-claim is transactional. Revocation fences new work; cleanup cannot create another assignment.

Authority fencing, physical shutdown and released mutable workspace ownership are separate facts. A local lease timestamp is not proof of termination. Keep uncertain machines counted until confirmed; do not transfer mutable ownership prematurely. Remote effects already started require reconciliation. Finite renewable leases bound orphan lifetime; unload persists retirement intent and attempts bounded cleanup, and re-enable reconciles. Provider failures back off rather than freeing phantom slots.

**Scheduling.** Codex is the default v1 harness. One fixed profile, small global/project limits, oldest pending request first. No fairness scheduler, warm pool or billing subsystem. Limits apply to Fleet machines, not external runners/research sandboxes. No automatic shared-VM fallback.

**Acceptance.** PostgreSQL concurrent admission; duplicate create/start/exchange; source revocation; stale epoch; cancel/claim race; unload; failed capture; uncertain provider stop. Then three independent code.v2 assignments on three real sandboxes, one injected failure, external runner coexistence, exact bases and retained review handoff. Confirm eventual cleanup and bounded State writes. Record startup/resource measurements. Rollback stops admission and drains while retaining domain records.

**Codex setup decision.** Package a pinned Codex CLI with Runner. Configure its existing codex profile and executable; Runner already prepares noninteractive launch and Merv MCP session access. OpenAI authentication is separate from Merv authority. Prefer API-key authentication for automated Fleet runs; a manually operated pilot can use a supported ChatGPT login. Current Runner forwards HOME/CODEX_HOME but does not forward OPENAI_API_KEY, so setting that variable on Runner alone is insufficient. Bootstrap must establish protected Codex credential storage for the execution identity, or a separately reviewed scoped provider path, and verify login before advertising readiness. Never bake credentials into the runtime image or put them in ordinary job env/commands. Model credentials are a separate secret boundary from the supervisor credential: do not assume supervisor UID isolation makes a credential accessible to Codex inaccessible to its tool subprocesses. Exact provider credential confinement must be tested before hosted rollout. See [official authentication guidance](https://learn.chatgpt.com/docs/auth).
