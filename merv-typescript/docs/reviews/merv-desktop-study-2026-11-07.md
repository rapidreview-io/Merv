Merv desktop makes the hosted board the place for thinking and the person's local Claude Code and Codex sessions the place for execution. It is a working Electron application with local persistence, runtime adapters, browser automation and a cloud bridge, rather than only an embedded website.

The desk listens on loopback and authenticates its API. Its database defaults to `~/Library/Application Support/Merv/desk.sqlite`. Electron supplies a fresh local token; desk startup removes that token from the environment before launching agents. The board's preload does not receive it. Closing the window leaves the desk alive; quitting stops its child process group. A shared Codex app-server has a separate lifetime. These are implementation boundaries, not a security certification.

## Runtime and authority distinctions

Claude uses the installed Claude Code executable through the pinned Agent SDK. It supports a streaming inbox, resume, rewind, compact, interruption and tool approvals. Existing Claude terminal sessions can be watched, but they are not live-joined. Elevating an existing Claude session to full access requires a new session. See [Claude runtime](../../../../merv-desktop/desktop/packages/runtime-claude/src/index.ts), lines 129, 294, 332–391.

Codex uses JSON-RPC over stdio or a shared Unix-socket app-server, normally `~/.merv/codex.sock`. Sessions started with `codex --remote unix://…` can be joined live; standalone terminal sessions are watched instead. Shared-server reconnect/resume, steering, interruption, rollback and compaction are implemented. Closing the adapter disconnects from a shared server rather than killing it. See [Codex runtime](../../../../merv-desktop/desktop/packages/runtime-codex/src/index.ts), lines 165, 228, 493, 541, 635–647, and [historical-session UI](../../../../merv-desktop/desktop/packages/desk-ui/src/app.tsx), line 1756.

Pairing redeems a one-time code and retains the resulting device identity locally. Folder grants distinguish mirrored access (`remote`) and board action access (`pi`). Commands carry IDs, expiry and target generations, are persisted, and must be revalidated after reconnect. Restart marks dispatched commands as outcome-unknown instead of replaying them automatically. Current board dispatch automatically enables the applicable folder grants and starts units with `access: 'full'`; direct session choices have their own permission settings. The README's older wording should not be read as a promise of a separate folder approval for every current board action. See [pairing and dispatch](../../../../merv-desktop/desktop/packages/desk-server/src/uplink.ts), lines 181, 749, 900–920, 975–983, and [restart handling](../../../../merv-desktop/desktop/packages/desk-server/src/store.ts), line 102.

Installed and authenticated local agent binaries remain prerequisites.

The desktop repository contains a separate copy of the hosted backend, not a dependency on this main checkout. [hosted/UPSTREAM](../../../../merv-desktop/hosted/UPSTREAM) records `80940ef4af8f9635172e3da288eaf14d4d7ee6cf` and `d95468428d971eca3c9419361a60e8b81eea6d9b`; desktop adds its own Desk integration and board changes. Consequently, fixes made in main Merv do not automatically update desktop's hosted copy, and desktop changes do not automatically update main. Synchronization needs an explicit comparison and port against those records, followed by validation in each composition. This is a maintenance boundary, not a claim that every divergence is a defect.
