# Native runner profile isolation

Audit date: 2026-09-15. Tested on this Mac with `codex-cli 0.155.0-alpha.2`, installed at `/Users/guraltoo/.nvm/versions/node/v22.13.1/bin/codex`. The conclusions below concern this installed CLI and the current [launch profile](../packages/runner/src/profiles.ts), not every Codex release or a full Git publication workflow.

The native profile gives a worker the frozen assignment, its session credential, a fixed MCP tool allowlist, and a filesystem sandbox. Repository instructions must not silently add tools, hooks, environment settings or automatic instructions to that launch. Native shell work remains available within the selected `read-only` or `workspace-write` policy. Explicitly granted MCP writes remain subject to Sessions authorization independently of the filesystem mode.

| Surface                           | Current control and verified scope                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User configuration and execpolicy | `exec --ignore-user-config --ignore-rules`; authentication still uses the installed Codex account through `CODEX_HOME`. The CLI documents these flags separately: ignoring user configuration does not mean ignoring skills. [CLI reference](https://learn.chatgpt.com/docs/cli/reference)                                                                                                                                                              |
| Repository `.codex/config.toml`   | Actual `exec` with the current flags omitted a synthetic repository instruction and did not launch a repository-configured MCP sentinel. Removing `--ignore-user-config` while the synthetic user configuration trusted the repository did launch that sentinel. This is an observation of the installed version, not a claim that all configuration inspection commands behave identically.                                                            |
| `AGENTS.md`                       | `project_doc_max_bytes=0`; its sentinel was absent from the actual outgoing model request. Files remain present and readable as repository data.                                                                                                                                                                                                                                                                                                        |
| Repository skills                 | Exact discovered `SKILL.md` paths are passed through `skills.config` with `enabled=false`. The actual request test below proves why this is necessary.                                                                                                                                                                                                                                                                                                  |
| Extra integrations                | Explicitly disables hooks, plugins, apps, subagents, browser/computer use, web search and automatic skill dependency installation. The profile configures Merv's MCP server with the lease's exact `enabled_tools`; server authorization independently enforces tool names and arguments.                                                                                                                                                               |
| Child environment                 | Copies only `PATH`, `HOME`, `USER`, `TMPDIR`, `LANG`, `LC_ALL` and `CODEX_HOME`, then adds the session token and MCP endpoint. It does not inherit the machine source key or arbitrary parent variables. Model-generated shell commands use a separate explicit environment without the session token or `CODEX_HOME`, with login/profile loading disabled. This is environment isolation, not a claim that the sandbox hides every readable host file. |
| Native filesystem                 | Uses the lease's read-only/workspace-write mode, approval policy `never`, no extra writable roots, no sandbox network access, and no implicit temporary-directory write grants.                                                                                                                                                                                                                                                                         |

Configuration tables require particular care: a synthetic trusted project configuration added another MCP server and shell-environment entries when its project layer was admitted. Scalar command-line overrides alone did not replace those whole tables. The official [configuration precedence](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence) explains which layers can participate; the actual `exec` probes establish the behavior used by this profile. Recheck these launch observations when upgrading the CLI.

The repository skill collector follows Codex's documented discovery locations: `.agents/skills` at the canonical working directory and its ancestors through the nearest `.git` directory or linked-worktree pointer file. Without a repository marker, it scans the working directory only. Sibling directories and descendants outside those skill trees are excluded. Host, admin and system skill locations are outside this repository collector. Codex follows symlinked skills; this runner instead refuses symlinks in the discovery roots and skill trees so they cannot escape the scan. [Official skill discovery and disabling instructions](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)

Discovery reads directory metadata, returns sorted canonical `SKILL.md` paths, and changes no tracked files. It fails closed after 4,096 skill-tree entries, beyond 32 nested skill-directory levels, or after 128 ancestor candidates. The controller collects the paths before calling the pure `buildLaunch`; the builder emits literal, validated TOML entries. `features.skip_host_skill_discovery=true` remains in the profile but is not relied on to suppress repository skills.

The actual request probe used a temporary repository, empty temporary `HOME`/`CODEX_HOME`, and a local fake Responses endpoint. It called the installed `codex exec` with the profile flags, bypassing only the unavailable fixture MCP server and substituting the local model provider. It captured the outgoing request and deliberately returned HTTP 400 before generation. Both runs therefore exited 1 with the expected `audit_stop_before_generation` message; these are successful prompt-inspection probes, not failed model acceptance runs.

| Repository skill description sentinel         | Present                           | Absent                                    |
| `AGENTS.md` sentinel                          | Absent                            | Absent                                    |

The checked-in [profile tests](../tests/runner-profiles.test.ts) passed 13/13, covering discovery boundaries, symlink refusal, entry limits, pure config generation and the existing launch controls.

Native Git permissions were checked separately using the installed `codex sandbox --permission-profile :workspace` with the profile's workspace-write settings. The fixture used a real linked worktree outside `/tmp`, with its Git administration directory outside the writable checkout. This avoids mistaking an implicit temporary-directory grant for permission to update Git metadata.

| Native sandbox operation                | Observed result                                                 |
| --------------------------------------- | --------------------------------------------------------------- |
| Append text to a checkout file          | Succeeded                                                       |
| `git add -- file.txt`                   | Refused: worker Git-directory `index.lock` could not be created |
| `git commit -am ...`                    | Refused at the same index lock                                  |
| Update the shared `refs/heads/main` ref | Refused: shared ref lock could not be created                   |

This matches Codex's documented protection of `.git` and the Git directory resolved from a worktree pointer. [Protected paths in writable roots](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots). Evidence: [sandbox results](/private/tmp/merv-codex-git-sandbox-audit.json) and [probe script](/private/tmp/merv-codex-git-sandbox-audit.mjs).

The current supported path is native file edits followed by runner-owned work-in-progress capture. It does not establish native agent `git add`/`commit` parity or a supported agent publication/merge operation. A future code-proposal and merge interface must provide that operation while preserving the boundaries around common repository state and other workers' metadata. Granting the child write access to the entire common repository is not part of this implementation.
