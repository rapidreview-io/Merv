# Reference translation for the Merv UI (panel, 2026-09-16)

Ten Opus agents read the founder's references (docs/UI_REFERENCES.md) and problemma.ai against the live code; a synthesizer merged their patterns into this plan. Treatments name the files and tools they rely on. "Now" items are the next phases of UI work; "later" items wait on the named server work or a ruling; "never" items are patterns the references have that Merv must not copy.

## Principles that fell out of the references

- Every number in the chrome means open-against-the-project; a thing you consult rather than work — a claim book, a record inventory, a file list — carries no number at all, and an absent value renders as nothing, never as zero.
- Colour means kind and nothing else: a state is a gray dot and a word, a verdict is a word in the review colour, and a claim's standing is never a colour a machine chose, because a contradicted hypothesis from a well-run, review-passed experiment is a good result.
- Three facts are never one word — execution state, review state and scientific outcome each get their own clause on the row and in the header, and any of them may read as absent rather than be guessed from another.
- A line that carries a control is addressed to you; a line with no control is an agent talking or a record being read, and that rule is what separates the feed's commentary from the record's authority without a second visual language.
- Every sentence about what may happen next is the server's own string — instruction, blocker.message, action.instruction, dependency.name — and the browser adds no rules, re-words no enum and never re-derives a readiness the workflow already evaluated for this caller.
- Evidence opens where it is cited and costs nothing until it is opened; a link that replaces the page with a file is a last resort, and the artifact page stays a destination rather than the only way to read a file.
- An exception is stated, never absorbed: a waived criterion, a verdict pinned to a superseded revision, a plan approved in an earlier attempt, an experiment that ended without a conclusion — each earns one plain, uncoloured line in the reader's path.
- Nothing in the browser may mark a reviewer's objection answered, hide a gate, or set a review aside; resolution is derived from a later finding on the same criterion text, and where the wording changed the page says it was not re-examined rather than inventing a closure.

## Now

### exp-record-order — The experiment record opens with the science, not the machinery (M)

Sources: W&B — the report order: narrative blocks first, run tables last; Benchling — one skeleton, always in the same order; W&B — collapsed headers defer their data

Surface: packages/ui/web/views/experiments.tsx — ExperimentRecord's twelve peer <section>s and ExperimentDetail's five polling useTool calls

ExperimentRecord stacks twelve sections whose h2.section-title all carry identical weight, so Conclusion competes with Record details and the page opens on What happens next — a paragraph about waiting, in front of a scientific record. Fix the reading order to a fixed skeleton that never varies with workflow.state: Question (e.intent set at 16px/600 directly under the title rather than as PageHeader summary text), Result (e.conclusion in full, with the exhibit as a captioned figure inside it), Assessment (the standing line and the rounds spine of the next two items), Claims tested. Everything that is bookkeeping — the Record details KV, the Attempts table, e.details, the manifest hashes — moves below one rule into a single Record block, which also deletes three section wrappers and lowers the net line count of packages/ui/web as the LOC rule requires. Render an empty slot as one muted line in place ('No conclusion recorded yet', 'No plan has passed design review') instead of vanishing, because a missing section and a missing fact look identical and the absence is often the finding. Apply the deferred-load discipline that views/reviews.tsx already gets right in its Evidence component: above the fold everything loads and keeps polling, while a sealed submission's evidence is requested only when its row is selected, so the page stops fetching five things every eight seconds whether or not they are on screen. The fold needs no chrome beyond the headings the page already has — the contract allows no disclosure triangles in normal use — and it sits in exactly one place, under the reviewed narrative. Do not make this a general accordion the reader expands section by section to find anything, and do not turn the page into an authoring surface: a Merv experiment page is generated from the record, never typed by a person.

Data: Verified all present and already fetched by ExperimentDetail. Experiment carries intent, details, conclusion, attempt, attempts, evidence, submissions, testedClaimIds and workflow (packages/experiments/src/models.ts); workflow.status_and_next and experiment.exhibit are already called. This is layout and call timing only — no new tool, no new field.

Why now: It is the founder's strongest recommendation — build the experiment detail around the review model and the evidence model — and it is the container every other experiment item drops into, so doing it second would mean rewriting the same file twice.

### exp-standing-line — Three facts under the title, and the drift between them (S)

Sources: GitHub — review decision at the top, pinned to the revision it judged; W&B — the snowflake: a frozen run set versus live state; Benchling — sealed on submission; Dagster — three states in one row

Surface: packages/ui/web/views/experiments.tsx — the PageHeader inside ExperimentRecord, which today carries one StatusPill on workflow.state

The header pill is execution state only; review state sits roughly four hundred lines below under a heading reading Current review, so a reader must scroll to learn whether anything passed. Replace it with a three-clause standing line directly beneath the title, one clause each and no boxes: execution (workflow.state), review (the newest submission's stage and round, its verdict word in the finding colour, the reviewer's name, when), outcome (a conclusion exists, or the tested claims are named, or 'no outcome recorded'). Add one quiet clause when the reviewed state is no longer the current state: the visible review pins subjectRevision, so when it differs from workflow.revision the line reads 'reviewed at revision 38, now at revision 41' — W&B's frozen-versus-live distinction expressed as a fact rather than a warning, and the same guard experiments.tsx already applies silently to guidance. Do the same for the plan when attempt.approvedSubmissionId belongs to an earlier attemptIndex, and give review.status === 'superseded' a sentence at last, since today it renders as a bare pill with no explanation of why the record was set aside. Where the verdict is pass and any finding is waived or not_verified, qualify it on the line — 'passed, 2 of 6 criteria waived' — linking into the rows that carry the reviewer's reason, because reviews.tsx already counts waived findings on its list page and then drops that qualification on the detail. Keep it text at 13px in the header block: no card, no second row of pills, so the title stays the dominant element. Do not add a green merge-style button and do not let Outcome be derived from a passing verdict — a completed, review-passed experiment that contradicted its hypothesis is a good result, and claim status stays a person's call through claim.update.

Data: Verified all present in calls ExperimentDetail already makes. experiment.get_state supplies workflow.state, workflow.revision, attempt.index, attempt.approvedSubmissionId and submissions[] with stage, round, attemptIndex, subjectRevision and reviewId; review.get (via visibleReviewId) supplies status, verdict, synopsis, reviewerId, subjectRevision and findings[].status; useActorNames supplies the reviewer's name. Nothing missing.

Why now: It is the first of the founder's two guiding distinctions, stated on the surface that matters most, and it is composition over data already on the page — the cheapest high-value change in the plan.

### exp-rounds-spine — Submission, criticism, correction, re-review as one spine (M)

Sources: GitHub — criticism, correction, re-review as one chain on the record; Dagster — the round spine as the record's timeline; Benchling — amendments add to history; Braintrust — objections that carry forward

Surface: packages/ui/web/views/experiments.tsx — replacing the Recovery and review feedback paragraphs, the Sealed submissions <details> stack and the Attempts table, reusing CriterionRows and Evidence from views/reviews.tsx

The chain already exists in the data and is rendered as three disconnected piles: attempt.feedback prints as untitled pre-wrap paragraphs, submissions become a reversed stack of collapsed summaries whose only route to the criticism is a link out to the review page, and attempts become a four-column table of revision ranges. Fold all three into one chronological spine, newest first, one line per submission: stage, attempt, round, pinned revision, verdict and return route — 'Results review, attempt 2, round 2, revision 41, needs changes, returned to running'. Expanding a round shows only the criteria whose finding was not_met or not_verified, each built from the parts CriterionRows already draws — the criterion text, the finding word in its colour, the reviewer's note, and the cited evidence opened in place — so a reader sees the objections rather than the roll call. Directly beneath each objection, when a later round carries a criterion with identical text, show that finding as the answer ('round 3: met — retrained with the held-out split'), which makes correction visible without anyone asserting it; where the wording changed, say 'not re-examined under the same wording' rather than matching by number, because criterion numbers are positional and a silent join would fabricate a closure that never happened. Attach attempt.feedback to the line whose review produced it instead of floating it in its own section, and use attempt.feedbackReviewIds — the server's own list of rejected assessments retained as context — to decide which prior rounds belong to this attempt rather than inferring from dates. Show the last three lines by default with the rest expanding, keep the wording neutral because needs_changes is a stage of the method rather than a failure, and refuse a Gantt: elapsed time between submissions is waiting for a reviewer, not compute, so segments carry words and not proportional bars. Nothing in the spine is editable or removable, and there is no control that marks an objection resolved.

Data: Verified. experiment.get_state returns submissions[] with id, stage, round, attemptIndex, subjectRevision, reviewId, producerId and manifestHash, plus attempt.feedback and attempt.feedbackReviewIds (packages/experiments/src/models.ts). ExperimentSubmission carries no verdict, only reviewId — confirmed — so the verdict per round comes from one review.list call joined on id, which returns full ReviewRequest records including findings, verdict, synopsis and returnTo (packages/reviews/src/tools.ts, index.ts list()). No N-times review.get, no schema change.

Why now: It is the founder's explicit GitHub borrow and it answers the brief's second question — why should I believe the result — with the one thing a record can show and a dashboard cannot. Caveat to raise with the founder: docs/UI_DESIGN.md defers 'the experiment record as an attempt spine'; this is the round-level version, which is non-empty today because rounds increment even while attempt.index stays 1, so it should be raised as an amendment rather than shipped as if approved.

### gate-box — One box that says what must happen before this advances (M)

Sources: GitHub — the merge box; Linear — meta properties to a side panel

The win is threefold: one idiom across experiments, cycles and reviews; a table whose only job was to restate two booleans disappears; and the net line count of packages/ui/web falls.

### verdict-desk — The blocker becomes the navigation, and the exceptions are stated (S)

Sources: GitHub — the pending review with a tray that counts what is left; Braintrust — the desk moves you to the criterion it is blocking on; incident.io — what the verdict did not settle

Surface: packages/ui/web/views/reviews.tsx — the Desk component's unmet computation, the CriterionRows list it governs, and the Verdict section

Desk already computes the right thing and wastes it: unmet produces strings like 'Criterion 3 still needs a finding and notes.' and 'Criterion 5 is met, so it must cite at least one pinned file.', and they render as static help text under a disabled button at the foot of a page whose criteria list can be long, so a reviewer scrolls back and counts list items to find number 3. Give each li.crit a stable id from its criterion number and render that sentence as a link to it, so the blocker is the navigation, and after a finding word and notes are entered offer one quiet text control reading 'Next unfinished criterion' that moves focus to the first row whose draft still lacks a status or notes, reusing the same predicate rather than writing a second rule. Dock a submit tray to the foot of the page for as long as the review is claimed: one line reading '4 of 7 criteria have findings · 2 claim met without citing evidence · synopsis 12/40', the verdict words, and the one primary control carrying unmet verbatim as its help text — GitHub's 'Viewed' progress as a fact about the draft rather than a self-report, since in Merv the numbers are derived and there is nothing to tick. Persist the draft and synopsis in sessionStorage under a key of reviewId plus subjectRevision and drop it when review.get returns a different subjectRevision, which is the honest analogue of a pending review dying when the branch moves under it. Separately, on a submitted review, put one quiet line directly under the synopsis naming the exceptions by number — 'Criteria 2 and 4 were waived; criterion 3 was not verified' — so a pass built on two waivers cannot read as an unqualified pass, and where the verdict is pass with any waived or not_verified finding that line is the second thing on the page. Do not editorialise: a reviewer waiving a criterion that does not apply is doing the right thing, so the line reports the exception without colouring it red. No progress meter beyond the tray's sentence, no per-criterion discussion thread, no verdict-free submission, and no behaviour that writes anything on movement — a Merv verdict is recorded once and cannot be changed.

Why now: The verdict page is one of the four surfaces docs/UI_DESIGN.md says design effort belongs to, the exceptions line is four lines of derivation over data already on screen, and the two together make the cost of reviewing legible while it is being paid rather than only when it is finished.

## Never

- **Snooze, mark-unread and delete on a review (Linear Inbox verbs)** — Those are notification hygiene. A Merv review is a gate holding a lease, and a reviewer who could snooze one would be hiding a blocked experiment from the only person able to unblock it.
- **User-tunable Priority — letting a person choose which types count as attention (Linear)** — Merv's priority rule is policy, already fixed in docs/UI_DESIGN.md and server-derived: input_required on a record whose producer is you, or an open review unclaimed or claimed by you. A tunable attention filter would let a scientist hide the very gate the review model exists to enforce.
- **Resolve conversation — any control that marks a reviewer's objection answered (GitHub)** — Nobody in Merv may set aside an objection by hand; the review record is immutable. Resolution is derived from the next round's finding on the same criterion, or it is not shown at all.
- **Reviewer rosters, N-of-M approval tallies, and a merge-style button in the record header (GitHub)** — A Merv review is single-reviewer, immutable and role-gated, so a tally would invent a process that does not exist, and advancing is an agent's move under workflow.status_and_next rather than the reader's.
- **A verdict-free Comment submission on the verdict desk (GitHub's third decision)** — review.submit requires a verdict and one finding per criterion. Offering a comment-only path would misdescribe the gate as negotiation.
- **Saved views, a view editor, Display menus, grouping pickers and chart configuration (W&B, Braintrust, Dagster)** — A persisted view entity for an audience of roughly one scientist per project, and docs/UI_DESIGN.md principle 3 rules out chrome in normal use. Grouping that is a property of the scientific record is hard-coded; grouping the reader chooses is a preferences popover.
- **A home screen of metric panels (W&B)** — The founder's brief rules it out by name. The Overview answers what needs me, what is running, what has been recorded — not what the numbers are doing.
- **A verdict read into a drawn graph: node status colour standing for scientific outcome, a currently-here marker, re-run or materialise controls, a minimap (Dagster)** — Every edge in a Merv graph is a recorded transition and nothing else. A derived process graph may say what the record did and when, but never whether the science it stepped through was right: the moment a node carries a green upstream state, a reviewed argument reads as an executed and passing one.
- **A selection-expression filter language (Dagster's key:/tag:/owner: grammar with traversal operators)** — It is a query language a person must learn in place of a control the contract already budgets — one search box and one secondary control. Merv's two real relations, tests-this-claim and judges-this-record, do not need an operator that reads as graph reach.
- **The Comparison grade — Improvement, Regression, Tradeoff, Tie (Braintrust)** — It pronounces on an attempt, which usurps both the reviewer's verdict and the claim's standing. Merv separates execution state, review state and scientific outcome precisely so no table can collapse them into a judgement.
- **Auto-advance and any control that commits on movement (Braintrust)** — A Merv verdict is recorded once and cannot be changed, and the desk's own help text says so. Movement may relocate focus and must never write anything.
- **Editing the timeline — retitling, hiding or annotating a domain event (incident.io)** — The record's authority comes from the events being untouched. Promotion, if it is ever wanted, is feed.post attaching a paragraph, not a pencil icon over an event.
- **Deadlines, reminders, assignees on obligations, and any row that turns amber because time passed (incident.io, Runpod)** — The brief says do not import urgency. Merv's ordering is blocker-derived, and a deadline would duplicate the review lease that already decides whose move it is.
- **Multi-stage sign-off (Approve then Witness), a Retract verb, and 21 CFR / audit-trail framing (Benchling)** — Merv has exactly one adversarial reviewer per review and a pass/needs_changes/fail verdict; a stage ladder would imply human approval of every transition. ExperimentTransitionName has no retract member, so a Retract control would promise an unsupported move.
- **Inferring supports-versus-challenges from conclusion prose, or any aggregate weight-of-evidence score on a claim (Elicit)** — Elicit can extract a passage's stance because the passage is prose about the claim. Here it would be a UI guess dressed as a finding, and claim status and confidence are a person's call through claim.update.
- **A PRISMA-style inclusion funnel, and a literature library with Zotero import, deduplication or PDF enrichment (Elicit)** — Merv's exclusions are a handful of records per claim, so a diagram makes a three-line fact look like a compliance artifact, and the citation ledger is a small hand-kept list whose value is the distinction it draws, not the corpus it holds.
- **Log tailing, download-logs buttons, and the billing frame (Runpod)** — Merv has no log stream — the retained evidence artifact is the log, and it is read, hashed and citable rather than tailed, which is the more valuable property and should not be traded for motion.
- **Re-specifying the problemma visual language: tokens, the white-card-on-light-ground rule, the kind colour table and the withdrawal of the serif** — Already shipped and still in flight in this checkout. styles.css now carries #f7f8fa / #ffffff, --kind and .record with its 3px kind edge; components.tsx exports KIND, kindOf, kindStyle and KindLabel; the Instrument Serif faces and fonts/ directory are deleted; shell.tsx and overview.tsx are being edited for it right now by a peer session. The remaining slices are the kind mark reaching the feed, review and knowledge lists, which ride along with other items.

#### tinker-estimated — Say estimated where a number is partial, and an em dash where it is not known (S)

Surface: packages/ui/web/views/overview.tsx (useDecisions and its eight fixed hook slots), views/feed.tsx (the activity column), packages/ui/web/shell.tsx TitleLine

`docs/UI_LEGACY_PATTERNS.md` checklist rule 4 already fixes half the policy — a fact the server did not send renders as nothing, a fact this record could have and does not renders as the faint em dash, a zero is only ever a measured zero — and Tinker practises the half Merv has not, which is that a number that is real but partial says so in its own label rather than in a footnote nobody reads. Two Merv numbers are partial today and say nothing about it. The standing line is capped at eight because `useDecisions` cannot call hooks in a loop, so a project with twelve blocked records shows eight and reads as the whole truth; give the block one muted foot line naming the cap in plain terms and pointing at the list that is complete. The feed's activity column pages forward from the oldest event through `feed.activity`'s `{ after }` cursor with no subject filter, so what it shows is a head window read best-effort; the column should say so once, where it ends, instead of implying the record stops there. Everywhere else hold the rule in the other direction just as hard: `liveSessionCount`, `sessionTotal` and the artifact totals are exact and must never be labelled estimated, because a hedge on an exact number teaches a supervisor to discount every number on the page, which is the same damage a lying count does. And follow the console on absence — a total that has not arrived yet is an em dash, never a spinner in a table cell and never a zero.

Data: Verified. `useDecisions` in views/overview.tsx is hard-capped at eight fixed hook slots, already recorded as the blocker under standing-line-complete above. `feed.activity`'s input schema is `z.object({ after: z.number().int().nonnegative().optional() }).strict()` — forward-only from the oldest event, no subject filter. `sessions.projectStatus` and `artifact.list` return exact values. No server change.

Why now: The two most-read blocks in the app are quietly incomplete, the repair is one sentence each, and it turns checklist rule 4 from a rule about missing facts into a rule about partial ones, which is the case Merv actually has.

#### tinker-primitives — The tool surface is the browser's whole vocabulary, and the grep proves it (S)

Sources: Tinker — "a small set of primitives that compose cleanly to express a rich space of algorithmic ideas"; Tinker — four documented verbs and a console that invents no fifth; Tinker — the primitive's own sentence reused wherever the primitive appears

Surface: packages/ui/web/views/reviews.tsx (the Controls component), views/experiments.tsx, views/claims.tsx, views/tasks.tsx, views/research-programs.tsx — every place the browser renders a control

Merv's primitives are already a short list, and naming it is the point. The composable set is `experiment.transition`, `review.start`, `review.submit`, `artifact.create`, `claim.create`, `claim.update`, `task.submit_delivery`, `task.mark_failed`, `feed.post`, `paper.patch`, `research.advance`, `reflection.submit_lens`, `reflection.submit`, `consolidation.submit` and `code.commit`; against them stands the one read that composes, `workflow.status_and_next`, whose `actions[]` carry `action`, `tool`, `instruction`, `status`, `arguments` and `requiredInput` — the server's own statement of which primitive this caller may apply to this record right now. Sessions are the instructive exception: `packages/sessions/src/` registers no tool at all, because a lease is something the runner moves and the browser reads through `projectStatus`, so there are no session primitives and the sessions page's Halt is the single operator control outside the set — which is precisely why it needs the consequence sheet the sessions-lease item describes rather than a button. The rule this implies has one clause: **every control in the browser is a named registered tool, labelled by that action's own `instruction`, dispatched to `action.tool`, and there is no second kind of control.** The verdict page's Controls component already obeys it; make it checkable everywhere else by grepping packages/ui/web for a control whose handler does not resolve to a registered tool name, at which point the Never list below reads as that check's expected-failures file — Resolve conversation, Assign, Retract, Snooze and the merge button are each a verb no `tools.register` call ever made. Hold the discipline in the other direction too: Tinker documents each primitive in one sentence and the console reuses that sentence verbatim, so where a Merv action carries an `instruction`, the control says it word for word and the browser writes no label of its own. The composition claim is the payoff — fifteen verbs and one guidance read express a review-gated research programme, and a UI that adds a sixteenth is not extending the system, it is describing a different one.

Data: Verified by reading every packages/\*/src/tools.ts (the names above are the registered mutating set; `artifact.get`, `artifact.read`, `artifact.list`, `experiment.list`, `experiment.get_state`, `experiment.exhibit`, `review.list`, `review.get`, `claim.list`, `task.list`, `task.get`, `project.records`, `project.references`, `workflow.status_and_next`, `workflow.process`, `feed.list` and `feed.activity` are the read set) and against `WorkflowDecision` in packages/contracts/src/workflow-guidance.ts. Every one is already reachable from the web package's call layer. No server change.

Why now: It costs a grep and a rule, it converts a scattered list of prohibitions into one positive test a future item can be measured against, and it is the founder's stated reason for adding this reference at all.

#### tinker-scope-and-prefix — Mine or everyone's, and a search: the only two list controls (S)

Sources: Tinker — the Sessions page: a "My sessions" scope switch and a search by session ID prefix, and nothing else; Tinker — the Checkpoints page: scope stated as a sentence instead of spent as a control

Surface: packages/ui/web/list-filters.tsx and its four consumers — views/experiments.tsx, views/reviews.tsx, views/tasks.tsx, views/sessions.tsx — with `useSession().actor.id` from shell.tsx

ListFilters spends both of the contract's control slots on the same axis: a search box, and a state `<select>` whose options are scraped out of whatever the list happened to load. counts-mean-open above already deletes that select and turns the states into a count line that filters; Tinker supplies what should take the freed slot, which is the axis Merv has never offered — mine against everyone's. Every list already carries the field: artifacts have `createdBy`, reviews `reviewerId`, sessions `actorId`, experiments and tasks their producer, and the signed-in actor id is already in the browser. Make the second control a two-value scope switch, default it per page by what the page is for — the review list opens on yours, because a reviewer's queue is the point, while the artifact inventory opens on everyone's, because a record inventory is a thing you consult — and put the scope's meaning in the empty state rather than a tooltip, which is where the contract says explanations live. Keep search as prefix-and-substring over the one or two fields a person actually types, exactly as ListFilters does now, and note that Tinker's search is deliberately a _prefix_ search over the session id: a person who has a hash from an agent transcript types the first six characters and stops, which is the real use and argues for matching the id prefix as well as the label. Then resist the third control permanently: the busiest table in that product has two. State-based narrowing is the count line's job, identity-based narrowing is the switch's, and anything beyond them is a saved view, which the Never list already refuses.

Data: Verified. `useSession()` supplies the actor (shell.tsx, views/claims.tsx already use it); `artifact.list` returns `createdBy`; `review.list` returns `reviewerId`; `sessions.projectStatus` returns `sessions[].actorId`; `experiment.list` and `task.list` return their producer. No server change; the switch is one predicate over lists already loaded.

Why now: It rides the same action-row rewrite as counts-mean-open and review-stances, so shipping it separately would churn four files twice, and it gives the freed control slot a use that no other reference proposed.

#### tinker-lease-inventory — What a lease left behind, counted on the lease's own row (M)

Sources: Tinker — the Sessions table counts Checkpoints and Checkpoint storage per session, joining its two durable objects on the row where the work is listed

Surface: packages/ui/web/views/sessions.tsx — inside the expanded two-line card the sessions-lease item builds, not as a column of its own

Tinker's best column is the join: a session row carries the number of checkpoints it produced and their storage, so "what did this run leave behind" is answered where the run is listed rather than on another page. The Merv version of that question is sharper, because a lease that closed having retained nothing did no recorded work at all, and the answer belongs as one clause in the sentence the sessions-lease item already writes — retained three files, 480 KB, or the plain fact that it retained none. Do not give it a column and do not build it as its own item: fold the clause into that card when it lands, so the sessions page gains a fact rather than a ninth cell.

#### tinker-scratch-resolver — The scratch surface Merv already has, given the Playground's manners (S)

Sources: Tinker — Playground: a scratch surface that acts on the product's own object and commits nothing; Tinker — prompt chips as the way in

Surface: packages/ui/web/views/knowledge.tsx — the ReferenceLookup form, its textarea and its `project.references` call

Merv's Playground exists and nobody would recognise it as one. `/knowledge` carries a textarea into which a person pastes up to two hundred record ids or `claim:`, `task:`, `experiment:`, `artifact:`, `review:`, `code-proposal:`, `code-commit:` and `session-final:` references, and gets back, per reference, a `status` of `resolved`, `missing`, `unsupported` or `unpublished` with the kind, label, revision and state. That is a real scratch surface acting on a real Merv object: it reads, it writes nothing, and it is the only place in the app where a person typing is legitimate, because a Merv record is authored by an agent under review and a person's prose has no authority anywhere else. Give it the Playground's two manners and nothing more. First the chips: three or four examples that fill the box, drawn from the prefixes the resolver actually supports rather than invented ones, so the reference vocabulary is learned by using it instead of from the placeholder. Second, keep the four statuses four different facts — `unsupported`, a prefix Merv does not resolve, must never render like `missing`, a well-formed reference to nothing, because the first is the reader's mistake and the second is a hole in the record, and today both arrive as a status word with no difference in weight. The payoff is the operational half of the contract's never-a-bare-identifier rule: every hash a person meets in an agent transcript, a log line or a founder's message gets exactly one home to be pasted into. Keep it on `/knowledge`, keep it folded, and never promote it to the rail — a resolver is a tool on a page, not a place.

Blocker: No data blocker. `project.references` is registered read-only, accepts up to two hundred refs, and views/knowledge.tsx already calls it. It waits on a founder ruling, because chips and a worked example read as chrome under principle 3 on a page the contract calls an inventory, and because this surface's home may move when the map lands and `/knowledge` is rethought.

### Never

- **The Playground read literally — a chat box with prompt chips against a model (Tinker)** — Tinker can offer one because its product is a model you can talk to and the scratch output is the thing it sells. Merv's product is a reviewed record: there is no endpoint to try, and a free-text box whose output is neither a post, a verdict, a claim nor an artifact would put a person's prose somewhere with no authority and no record, which is the exact confusion the commentary-versus-authority rule exists to prevent. The reference resolver above is the only scratch surface Merv gets.
- **Usage and Billing as planes of the product: three summary cards and a spend chart (Tinker Admin)** — It is the home screen of metric panels the founder's brief rules out by name, wearing a different hat. Merv's compute facts belong to the lease that incurred them, on the sessions card, in research terms.
- **Publish, unpublish, push-to-Hugging-Face and set-ttl on a retained object (Tinker checkpoint CLI)** — "Only the owner of the training run can publish checkpoints" is the right rule for weights a user owns and the wrong shape entirely for evidence. A Merv artifact is pinned by a review and cited by a finding, so a control that could make it public, private or expiring would make a settled verdict's evidence negotiable after the fact. Deletion goes the same way: Tinker's "WARNING: This action is permanent and cannot be undone" guards a thing a person owns, while Merv registers no artifact-delete tool at all and must not acquire one.
- **A Perfetto timeline export per session (`tinker session export-trace`)** — A microsecond trace opened in an external viewer is a performance engineer's instrument. Merv's retained evidence artifact is the log, and it is immutable, hashed, citable in a finding and readable in place, which is the more valuable property and must not be traded for a timeline.
- **An untyped Metadata column (Tinker's Sessions and Checkpoints tables)** — Both tables end in a dictionary the product cannot say anything about, so the column is a shrug in the position of a fact. Merv's equivalents — role, stage, attempt, revision, verdict, outcome — are typed, and each belongs in a named column or in the panel, never pooled into one.
- **The storage path as the object's visible identity (`tinker://run-id/sampler_weights/final`)** — Merv identifies a retained file by its hash and names it by its title, and adding a path to the row would be a second identity to keep true, on rows whose whole purpose is that the identity cannot drift.
- **The sterile half of the minimalism: grey-on-white as the whole palette (Tinker)** — The founder took the restraint and refused the colour in the same sentence. Stripping the border is the borrow; stripping the kind colour and its icon with it would be the mistake, because a Merv row's first fact is what kind of record it is, and a page of undifferentiated grey rows would cost the one device that carries the rail, the title line, the record edge and the legend at once.
- **Estimated as a hedge on an exact number** — The borrow above is narrow on purpose. `liveSessionCount`, `sessionTotal` and a summed artifact size are exact; labelling any of them estimated because it feels safer teaches a supervisor to discount every number on the page, which is the same damage a count that means inventory on one row and attention on the next already does.
