# Fleet

Fleet is a default-disabled, server-side capacity and sandbox lifecycle service. It does not run research work or expose allocation requests as agent tools; its list, get, drain and halt tools answer with the same redacted view as its page, without an allocation's source, person or launch ids. A trusted owner registers to validate authority, provide stable bootstrap bytes, and report when capture or checkpoint work has finished: Pi registers `pi-host` whenever it is enabled, and the optional workflow adapter registers `workflow`.

An allocation uses one immutable runtime profile and stable create and launch keys. Global and per-project limits count every allocation that has left the queue until terminal provider evidence permits release, or Fleet proves the allocation never had a possible machine effect. A queued request gives up at its deadline; once reserved, the machine gets the full allocation timeout. Reaching a deadline requests cleanup and retains the reservation. `drain` prevents new admission and launch while renewing a running sandbox until its owner finishes or the deadline expires. One failed call keeps a launched machine's phase, and its worker's admission, while its lease lasts.

The workers Fleet launches hold no model provider key. `fleet.modelRelay(config)` builds the relay that holds it for them (`src/model-relay.ts`): a feature supplies its route, bearer, grant, accepted bodies and spend hooks, then mounts the relay's handler public on the API and closes it with the mount. Pi does this for `/pi-model`, and the workflow adapter for hosted Codex at `/codex-model`.

Fleet records `createAttempted` and increments `createAttempts` before contacting the provider. A request from a project without a connection or grant is refused, and an untouched stopped allocation releases without renting a machine. A definitive no-effect refusal of the provably sole first create permits release with `runtime_refused` (or `wallet_refused` for a wallet refusal). A refusal of one concurrent invocation cannot prove that another invocation had no effect. Ambiguous failures, including timeouts, conflicts and rate limits, retain capacity and retry the same key.

Once stop is requested, an allocation without a handle repeatedly tries same-key recovery under its original profile so Fleet can discover and delete a machine made before a lost reply. A deleting machine remains counted until the provider confirms it is terminal. An unreachable machine, a lost connection, or a removed profile can hold capacity indefinitely. This trades automatic reclamation for safety: create or renew work already dispatched can take effect arbitrarily late, including after cancellation and restart. Cancellation prevents new renewals but cannot retract an already pending one. A queued successor waits until terminal evidence permits release.

Elapsed time never releases an attempted allocation. Legacy `releaseBy` deadlines are ignored and cleared during cleanup; the original `leaseSeconds` and greatest observed `leaseExpiresAt` are diagnostic evidence only. There is no assumption that all operations finish within 60 seconds or that lease expiry alone proves termination. Provider contracts remain essential: each stable key identifies at most one machine; stopped/deleted keys retain permanent tombstones that neither create nor renew can revive; terminal observations and definitive no-effect refusals are truthful. A successful DELETE returning `deleting` is not terminal evidence. Fleet checks machines each poll interval, and every second only while one is starting, stopping or due for a retry.

Daily compute budgets include every open rental regardless of its creation date and every rental released during the current UTC day. Long-held cleanup therefore continues to count, and a release today does not erase today's spend. The calculation uses the recorded runtime and reservation price; requests without a recorded machine cost nothing in this estimate. The released-person index added by migration V3 supports the recent-release query without changing earlier migrations.

The separate Sandboxes control service currently has a [reproduced terminal-report race](../../verification/provider-boundaries/README.md): it can report stopped while an older create is still paused. That provider contract remains an open defect; these local Fleet rules do not establish a physical machine limit against a provider that reports termination too early.

The service does not prove a runner is alive from the Sandboxes launch receipt. The owner observes runner enrollment and completion. Fleet admission requires a confirmed launch, current source authority, matching epoch and profile, and `run` intent. Owners with claimable work must recheck completion through `canRetire` in the writer that sets stop; the workflow adapter does so, and a vetoed retirement still performs due renewal. Shutdown fences admission, requests cleanup, and leaves pending provider deletion for a later controller to reconcile. Closing leaves to the successor the allocations of kinds never registered in this process, a kept owner's running work in every phase, and any stopped allocation without a machine handle, such as a create whose reply was lost. Fleet stops the work of a kind with no registered owner only from five minutes after Fleet starts, so a restart does not stop work whose owner registers late. Protected runtime sandboxes never appear in the project's Sandboxes rows, and the sandbox tools refuse them.

[The Fleet verification notes](../../verification/lean/FLEET.md) describe four kernel-checked models: reservation/admission (`Fleet`), lease diagnostics (`FleetLease`), conditional owner retirement (`FleetWorkflow`), and provider/controller release interleavings (`FleetRelease`). Finite conformance tests compare the model CLIs with real Fleet services and PostgreSQL under a controlled fake provider. The historical timeout counterexample is kernel-checked and retained as an `oldTimeout: true` negative control that the comparator must reject; it is not a current expected production bug. These checks do not establish full implementation refinement, remote provider compliance, or eventual cleanup.
