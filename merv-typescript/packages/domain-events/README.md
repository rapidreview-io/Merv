# Domain Events

Provides `domainEvents`; requires only `state`. This is durable business-event delivery, separate from Cordis's in-memory lifecycle events. No tools, message broker or external worker is required.

Publishers append events through State in the same transaction as their change. They do not depend on delivery being available. Consumers register a stable ID, distinct event types, an explicit first-install position (`beginning` or `now`), and a handler that may await database operations. Reinstalling the same ID always resumes its persisted cursor. Changing subscribed types requires a new ID and an explicit replay choice.

The dispatcher processes the event log in sequence for each consumer. It awaits the handler before committing its effects and the consumer cursor in one State transaction. Rejected handlers roll back both; a separate transaction records a sanitized error code, retry deadline and attempt count. A failed consumer stops at its failed event; other consumers continue. No event is silently skipped. `await ctx.domainEvents.status()` exposes active consumers, progress and failures. The shared dispatcher uses post-commit wakeups, bounded batches, retry backoff and a 100 ms safety wakeup to discover commits from another State connection. Background storage failures are contained and retried; explicit `drain()` callers receive failures that cannot be recorded.

Event records cannot be updated or deleted. This initial implementation retains the complete log and performs historical replay for new recovery consumers; it has no pruning or automatic dead-letter skipping. A permanently failing handler needs a code/configuration repair. Normal unload unregisters handlers without deleting their progress. The subscription disposer withdraws new admissions immediately and joins an admitted handler transaction before the owning plugin closes. A handler can detach itself without waiting for its own transaction. Concurrent `drain()` calls join the same pass. An active handler cannot drain or close its own dispatcher: those calls reject with `events_handler_active` before changing lifecycle state, because waiting for the current pass would wait for the handler itself. Dispatcher close stops timers and joins pending registrations and admitted work before State closes. Restart replays pending work.

This version targets one application runtime per database and short local handlers. Await every asynchronous operation that belongs to the handler. Do not perform network calls or launch agents inside a handler transaction. Local effects plus progress have an atomic commit; remote effects do not acquire an exactly-once guarantee. Runner launch/cancel work must use separately persisted and reconciled commands.

Reviews is the first production consumer: `reviews.actor-revoked.v1`. Its cleanup runs as trusted plugin code, not as the revoking operator. The derived event preserves the initiating actor ID and records `performedBy: system:reviews` plus the causal event ID. Revocation remains effective even when delivery or Reviews is unavailable. Cleanup is eventual and its failures remain inspectable.
