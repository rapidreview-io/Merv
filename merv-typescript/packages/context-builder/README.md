# Context Builder

Provides `contextBuilder`; requires State, Scope and Artifacts. There are no context-adapter plugins and no new context-specific tool adapter. Existing Tasks owns task-type definitions and registers their recipes directly.

A type definition contains a name, immutable version, assignment kind (`work` or `review`) and a declarative recipe: instructions, ordered sections, required/optional inputs, output instructions and a character budget. Registering returns a lifecycle-bound build/replay handle and disposer. Replacing a published recipe requires a new version. Reinstalling an identical version is supported.

Build inputs identify the subject/revision/current review claim and provide named text or artifact references. Unknown inputs fail. Required sections and instructions must fit in full; optional background is considered afterward and omissions are recorded. Budgets count JavaScript string characters, not model tokens. Artifact input mode defaults to strict UTF-8 text. Explicit `auto` includes readable text and binary metadata references; `references` includes metadata only. Binary references retain ID, hash, media type and size in the prompt and source manifest; no arbitrary filesystem paths, HTTP fetches or executable templates are evaluated. Document content is identified as source material and carries artifact IDs and hashes.

A successful build persists an immutable context package, its rendered prompt, actor/project identity, source manifest, recipe hash/version, subject revision, optional claim ID and content hash. Package persistence, command deduplication and the `context.built` event commit together. Reusing a request ID with different explicit build inputs fails. An owning registration can `replay` the previously saved package by the same subject/request ID after rechecking current domain permissions; this verifies recipe identity and subject, preserving snapshots across deployment or progress changes. Tasks does this only after current assignment checks. A new request ID creates fresh context. `get(caller, contextId)` lets the package's actor or a project operator inspect an old package even after the recipe is unloaded; revoked actors cannot access it. Old packages remain historical records, not permission to act on an obsolete claim.

Tasks validates current assignment ownership, workflow revision and reviewer claim inside the same transaction before invoking the builder. It exposes `task.context` over HTTP/MCP. Other domain plugins can register recipes through the same service; the builder contains no task-, review- or experiment-specific selection rules.

Tasks registers `task.work@1` and `@2`, `project.reflection@1` and `task.review@3`; experiments and reflections register their own. Retired recipe versions, such as `experiment.plan@1` and `@2`, stay in `context_recipes` as history, while the packages built for retired work items were deleted with those items (context_builder migrations 2 and 3). Reflection is a typed task assignment using explicitly supplied artifact inputs and the existing delivery/review workflow. They do not implement experiment execution, automatic corpus search, a multi-agent reflection workflow or a Runner.
