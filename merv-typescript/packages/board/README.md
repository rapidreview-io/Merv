# @merv/board

Personal-agent tools below use `{"action":"x","x":{...}}`.
Leased workers keep the alias names and inputs granted by their pinned workflows.
See the [tool overview](../../README.md#agent-tools).

Board keeps a project's whiteboards: unlimited boards per project, for ideas. People draw on them in Excalidraw on the **Board** page, and their agents draw on them with `board.write` (`draw`). A board is a living record, not a file: each shape is stored at its newest version, so a person, a colleague and an agent drawing at once merge shape by shape, as Excalidraw itself reconciles. Beside that stands its [history](#history-and-replay). It creates no workflow and is never part of a record of the work.

## Where it sits

Board requires State and Scope and nothing else. A card that links to a task, an experiment, a file or a paper keeps only that record's id (`merv:<id>`, or a web address); the page names and opens it through `project.read` (`references`), as a link in any text is, so Board reads nothing of other plugins and none of them knows boards exist. Its row declares `opens: 'board_'`, so a board's id opens on its page wherever it is named.

| `@merv/board`       | State, Scope | Boards, their shapes, images, revisions and history; `board.created`, `board.changed` and `board.set` events                                                                                                                                                                               |

## The agent's tools

`board.read` with action `list` lists boards; action `get` with `get.board` says what one holds: frames, shapes with their text and rough place, link cards with what they open, and arrows with the shapes they join. `board.write` (`draw`) makes changes in one atomic call of composable operations, and the guide asks an agent explaining something visually to build it up in several small calls in a row, without waiting for a person, so they can watch it emerge. The operations are `note`, `box`, `text`, `link`, `arrow`, `frame`, `flow`, `image`, `edit`, `move` and `delete`, and some can be [proposed](#proposals). A new shape goes `near` a shape (the nearest room around it, on a `side` if asked), `in` a frame, `at` an exact corner in the coordinates `board.read` reports, or into the next free place; Board works out the rest (`elements.ts`). `sketch` draws pen strokes from SVG path data (`path.ts`). Keys name what a call makes, so its later operations can point at it. To see a board as drawn (handwriting, a sketch, a layout), the agent looks at it by its id: Board contributes an actual Excalidraw image renderer to Tools (`renderer.ts`, fitted to a `focus` or camera region), so the look needs nobody's screen.

## Where agents are

A page shows each agent on its board as a small named cursor, with Excalidraw's own collaborators: where it last looked (`board.read` `look`) or drew (`board.write` `draw`), as `looking` in `board.scene`, which the page polls, for 20 seconds. Pi is `Pi`, a leased worker `Worker`, an outside agent its MCP client's name. The cursor slides to the middle of that region and, while a stroke drawn there is traced, rides the pen's tip; it dims at 16 seconds and goes at 20, the only fade Excalidraw draws, and under `prefers-reduced-motion` it does not slide. A collaborator is the page's view state: a cursor is never saved, changes no version and enters no undo. The guide asks an agent to look at a shape before naming it, so its cursor lands there, but in trials agents answered from their first look at the whole board (0 of 17), so the cursor usually stands in the middle of what it saw. Excalidraw colours a cursor by a hash of its id alone, so `board-presence.ts` picks the id that comes out the board's blue, and its list of avatars is hidden.

What an agent was doing is kept in Main's memory, like its cameras: Main is one process (`deploy/compose.yml`), and a restart forgets it. A second Main would show only the cursors of agents served by the process a page polled. A page's own draw (`isAgentAudience` is false) shows nothing, and neither does anything a script does through `/tools`.

## What the person points at

What is selected, pointed at or just circled on a board goes with what the person says to Pi, typed or spoken, as a note in ids and numbers: `[board b: selected a,c; pointer at (x,y) near d; circled e,f]` (`board-pointing.ts`). The pointer counts where it stopped for 300 ms, so crossing the board on the way to the composer does not move it; a circle is a closed freehand stroke of theirs from the last 20 seconds, with the shapes whose middles it holds; each goes with one message. The page gives it to `pi.send` as `pointing`, beside their words, and Pi opens the turn's context with it, which is labelled source material, not instructions, and rides that turn's requests alone: their message, the transcript and the conversation's history never hold it. `pi.send` refuses a note not in this form, ids and numbers alone, and a retry goes with the note it first had. Only the Agent's own composer on the board page carries one: an outside agent's person points by telling it.

## Proposals

An agent checks what it understood by drawing it. `proposed` on a `note`, `box`, `text` or `sketch` operation draws it faint and dashed, with `customData.proposed`, and all a call proposes stands in one group, which its answer names as `proposal`; a guess split over two calls is two proposals. `get` reports `proposed: true` until the person answers. Selecting a proposal shows a ✓ and a ✕ above it (`board-proposal.tsx`): ✓ makes its shapes ordinary and ✕ deletes them, each a change of the person's, so it is saved, in history and undoable. The guide tells an agent asked what a sketch is, or unsure what a mark means, to draw its guess this way and ask, rather than say. Arrows, cards, flows, frames and images are not proposed.

## Bringing things onto a board

The page has one panel for it, opened by the + at the end of the shape toolbar or by ⌘K (Ctrl+K elsewhere) when the board has the keys, with or without a selection. It lives in the UI layer (`views/board-add.tsx`) and adds through `board.write`, so Board still reads no other plugin. It takes ⌘K ahead of Excalidraw, whose hyperlink editor stays on a chosen shape's Link button and right-click menu. Its tabs are Boards, Files, Records (tasks and experiments from `ui.home`, papers the paper cites), Collection and Link, most recent first. A JPEG, PNG or WebP file lands as the picture (the `image` operation), and if that fails, as a card; everything else is a card. A paper's card opens its address, because a citation is no record `merv:<id>` can name. A file uploaded in the panel or dropped on it is saved to the project's Files and placed in one go; an image pasted or dropped on the canvas stays on the board only. What is added lands to the right of the selection, otherwise in the middle of the view, clear of what stands there, and ends up selected. A picture's height is known only once it is drawn, so one that turns out to cover something moves off it in a second save.

## What a board keeps

Rectangles, ellipses, diamonds, text, arrows, lines, freehand strokes, frames and images. Embeds and iframes are refused: a board loads nothing from elsewhere. A link is a web address, a Merv record or an in-app path. A board holds at most 5,000 live shapes; a page saves at most 500 shapes a call. A deleted shape is kept on the board 30 days (and in history for good), so a page that missed its deletion still learns of it; after that the board's next change purges it (at most 500 a change), and a page asking for what changed since before a purged deletion is handed every live shape, marked `whole`, in place of the changes. Archived boards leave the list and stay retained. Everyone in the project can read and write boards, including readers, reviewers and all Fleet worker roles. Drawing is shared collaboration outside frozen workflow grants; it does not grant code, artifact or research-record writes. Work visits still require a live lease and acknowledge pending messages; inquiry visits require live session and source authority. Project isolation and revocation checks apply to every edit.

## Images

A person adds an image by pasting it, dropping it on the canvas or with Excalidraw's image tool. PNG, JPEG, WebP and GIF, up to 10 MiB each; the page says why anything else is refused, and Board refuses it again by the bytes themselves (never SVG, which can carry script). Excalidraw shrinks what it is given to 1,440 pixels on its longest side and draws a GIF's first frame, so that is what is kept.

The bytes go to `PUT /board-images/<file>` before the shape is saved, and every page brings them back from `GET /board-images/<file>`: both answer to the bearer's membership of the project, on every request, with nothing cached and no link to pass on; a platform administrator reading the project is not shown them. They live in Board's own `board_images` table, under the project and the name Excalidraw gives the file (the hash of the file as chosen), so the same file is kept once per project and Board needs no plugin beyond State and Scope. A tool's JSON cannot carry them, so `@merv/board/tools` mounts these routes when the API is there.

Bytes last as long as a shape can name them, on any board of the project, a deleted one's 30 days included, and as long as history shows them. When a change purges a shape, what no shape of the project names and history never showed goes too, with anything stored over 30 days ago and never drawn. `board.read` (`get`) says an image is there, with its place, size and any `alt` and `source`, and `look` draws it, each under the same membership. A look draws at most 32 MiB of images; past that the rest are placeholders until a closer look.

An agent places one with the `image` operation of `board.write` (`draw`): `{op:'image', artifactId, page?, region?, alt?, width?, near/side/in/at, key?}`, from a JPEG, PNG or WebP artifact or a page of a PDF artifact, cropped to `region` in the pixels `artifact.read` (`look`) reports for it, so it can be checked first. Board reads no other plugin for this: the tools ask `tools.picture` for the record, under the caller's own access, as any look does, and it answers where Artifacts has contributed a drawer. What comes back is a JPEG of at most 1,600 pixels on its longest side, flattened on white, as Excalidraw shrinks what a person pastes: the original bytes are not kept, so a source over 10 MiB is taken while it is within Artifacts' 16 MiB, and the 10 MiB limit and the content check apply to what is stored, through the same `storeImage`. It is then an image shape like a pasted one, for moving, resizing, replay and looks, and arrows bind to it; `customData.source` says what it was taken from, and `get` reports that. At most 8 a call; bytes are stored ahead of the call's transaction, so a call that then fails leaves them to the same purge as anything stored and never drawn. Server-side fetching of an image by web address is not offered: a board loads nothing from elsewhere.

## History and replay

Every change to a board also writes a step of its history (`board_history`), in the same transaction: its revision, who, when, and the shapes as they became, in the order they came. People's strokes are kept as well as agents' drawing. An agent's every `board.write` call is its own step. One person's saves within 5 seconds are one step, up to about 1 MB, so history is not a row every 600 ms: a shape saved again stands where it first came, as it last was, and what it was in between is not kept. Any other actor's change or a draw ends the step, so order between actors holds and the board can be rebuilt exactly at the end of every step (`boardAt`), never inside one.

History starts when this ships. A board older than that begins it, at its next change, with one `before` step: how it stood then, shown as it stood and never played, since how it got there is not known. History is kept for the life of the board, **erased work included**, and the bytes of every image it shows with it: the 30-day purge of deleted shapes from `board_elements` does not touch it. There is no retention limit and no way yet to clear it, so it grows with what is drawn: a person drawing without stopping for an hour writes up to 720 steps. `board.history` reads it a page at a time (100 steps or 2 MB, and always the next step), to project members alone, as image bytes are: a platform administrator reading the project is not shown it. No agent can read it: it is not in `board.read`, and it is page-only.

On the page (`board-player.ts`), watching and replay are one player given shapes in order. Watching, it keeps up with what the 1.5-second poll brings: a shape from elsewhere joins the scene only when its turn comes, bound labels with their box and a card's parts together, and a new freehand stroke, line or arrow is first traced on a canvas of its own above Excalidraw. Nothing it has not landed is in the scene, so nothing animated can be saved, change a version or enter undo, and a reload shows the real board. It waits while the person is mid-gesture (a stroke, a drag, typing, an image being placed), never animates what the scene already holds, shows everything at once under `prefers-reduced-motion`, and speeds up to stay within 4 seconds behind. A freshly opened board shows its state at once. Replay feeds the same player history from the start in a read-only Excalidraw of its own, over the live board, which goes on underneath; it has no way to save, and "Back to now" takes it away.

Concurrent drawing still merges shape by shape, newest version winning, and history records what each change kept. Where two people add a shape at the same fractional index, each page ranks the clash alike and keeps that to itself rather than saving it as a change, until someone next edits the shape. `tests/board-replay.test.ts` covers history and `tests/sessions-api.test.ts` its refusal to leased workers; the page's behaviour was walked through in a browser, not automated here.

What this does not do: a poll's shapes play by fractional index, so an agent's shapes play in the order drawn, but two calls within one poll run together; steps from the same person in another tab play as anyone's; a stroke being traced is a plain pen line until it lands, when Excalidraw draws it with its own roughness, dashes and arrowheads; replay reads all of a board's history into memory when opened and does not follow what is drawn after; and a sequence shows what was drawn when, never why, so it says nothing of what anyone meant.

## Direct visual feedback

`board.read` (`look`) with `board` naming a board returns a JPEG exported by the same Excalidraw
package as the editor, directly to the agent. The offline Chromium renderer restores elements
and bindings, loads bundled fonts before measuring text, and never changes the stored scene.
New sketch paths use native lines with zero roughness and fixed widths; saved freehand drawings
remain intact. Notes, labeled boxes, text, frames, links and flows retain their existing inputs.

Optional `view` accepts `fit`, `region` (`x`, `y`, `width`, `height`), `pan` (`dx`, `dy`), or `zoom`
(`factor`, optional `center`). Coordinates are board units. An omitted view preserves that
conversation's last camera on this board; `focus` fits a shape, frame or sketch group.
Camera state expires after an hour and on server restart. Up to 1,000 recent cameras are kept.
The renderer bounds image size and rendering time, closes failed pages, and restarts a disconnected
browser. Pi retains the two most recent images in model requests and clips older views when
saving bounded conversation history; inspect the board again when returning to an older detail.
Other pages retain their existing text-description feedback.

`npm run build` packages the offline browser bundle and font manifest. For source development,
run `npm run build:board-renderer` once after installing dependencies. Chromium is the existing
production Playwright runtime used by Reports. `tests/board-vision.test.ts` also accepts
`MERV_TEST_CHROME` to select a local browser executable.

`board.read` (`look`) uses ordinary project read permissions. Leased workers retain the `board.look` alias and flat inputs until their pinned workflows drain. Outside a conversation, camera state is not retained: use an explicit region or focus for repeatable detail views. The older `screen.read` (`look`) with `at.record` board route remains compatible and shares the renderer and conversation camera.
