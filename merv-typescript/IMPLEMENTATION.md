# Merv TypeScript implementation

Scope: twelve independent Cordis component packages, durable task/evidence/review loop, project feed, HTTP and MCP, live tests by fresh Codex processes, and feed removal during an active MCP call. Existing Python code is untouched. No UI or automatic runner is required in this slice.

Shared contracts live in `packages/contracts`; Feed owns its public interfaces and Context augmentation in `@merv/feed/types`. Components import public types instead of sibling implementations. Upstream Cordis Loader imports configured plugin modules; bootstrap owns only composition and readiness policy. Feature adapters are owned by their component and inject `tools` plus their own service. Core services never require the tool registry. Synchronous SQLite transactions are explicitly passed across component interfaces when a task transition and review verdict must commit together. Runtime unload never deletes durable records.

Validation must cover real SQLite persistence/restart, migrations, immutable bytes, cross-project authorization, review independence and snapshot pinning, workflow versioning and request deduplication, atomic task/review routing, registry disposal, HTTP/MCP clients, and fresh Codex producer/reviewer sessions.

Feed depends only on state, scope, and artifacts. No other domain service depends on feed. Its optional adapter owns four tools and waits for admitted calls when disposed. Removing the provider must let Cordis suspend the adapter automatically, without restarting unrelated services; reinstalling the provider must reactivate that same adapter and expose retained posts and activity. The repeatable acceptance scenario uses real HTTP/MCP and one explicit handler barrier to guarantee overlap with disposal.

Plugin configuration lives in `config/default.json` or an explicit JSON file. The loader owns activation and completion; required-entry checks separately reject initialization/validation failures and missing dependencies. Runtime operations use stable entry IDs, and status resolves current fibers after replacement. Configuration and runtime status are separate: diagnostic output excludes plugin config values.

External tool transport uses validated MCP JSON Schemas and separate catalog generations in the existing generic registry. Mounted names use a reserved prefix; local project selection uses HTTP/MCP metadata so remote arguments are preserved. The registry captures each admitted definition and drains its generation before disposal. An independent HTTP/SSE fixture exercises pagination, notifications, schemas, multimedia/structured results, and errors. Upstream discovery and credential-scoped clients are owned by the independent Mounts plugin.

Access and Credentials are independent Scope consumers with their own public types. The registry requires Access and filters remote discovery/invocation using the current caller. Credential selection remains a separate server-side contract; a scoped SDK client helper consumes it and rechecks authority before dispatch after connection setup. The full API configuration installs both providers with empty defaults. The optional Mounts plugin uses these providers; an explicitly authorized fresh-agent sandbox `usage_report` call has been verified.

Mounts depends on Tools, Credentials, and Access through their public contracts. Its own public types live at `@merv/mounts/types`. Each configured mount owns a catalog namespace, dedicated discovery connection, scoped invocation pool, and bounded refresh/backoff timer. Tool selection precedes schema compilation. Whole-plugin disposal initiates every catalog withdrawal before waiting for any admitted call or dependent status consumer, then closes all resources and reports sanitized cleanup failures. The upstream Cordis loader may still log rather than propagate disposal errors; application completion must not be mistaken for proof that every possible cleanup failure propagates.

The configured mount-removal scenario uses actual Cordis Loader, SQLite, HTTP/MCP, and a separately authenticated upstream fixture. It preserves native task/review/feed work across removal and restoration. Real sandbox source/discovery preparation selects only `usage_report`; authenticated live verification passed with one scoped `usage_report` call; the additional Fable consultation is being completed before advancing.
